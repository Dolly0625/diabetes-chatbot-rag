> 文件目的：確認產品使用情境、目標架構、分期方向與第一階段交付範圍

## 一、計畫摘要

本計畫擬建置一套面向 **糖尿病患者、病患家屬及醫護人員** 的角色感知、證據導向之糖尿病資訊與安全支援人工智慧代理系統（Agent）。產品先聚焦於已有研究與實作基礎的三項任務：**糖尿病衛教與自我管理支援、看診前資訊收集與整理、醫護端證據查詢與衛教草稿**。系統不自行診斷或調整治療，而以目前已建立的證據檢索、證據審核、證據式生成、輸出檢查與執行軌跡為安全骨架。

本計畫不以一次建成可自由操作所有工具的通用醫療 Agent 為目標，而採取分期、可驗收的演進方式：先將現有檢索增強生成（Retrieval-Augmented Generation, RAG）能力封裝為資料來源可替換的標準化檢索工具（Tool），建立統一工具資料契約（Tool contract）、執行器與追蹤機制；再逐步加入角色與任務分類、多來源工具及受限工具選擇。所有工具回傳內容均視為候選觀察結果（observation）或候選證據（candidate evidence），必須通過既有的政策、證據與輸出安全邊界，才能形成對外回答。

預期最終成果是一套可擴充、可追蹤、可驗證，並能針對不同使用者完成明確工作流程的糖尿病對話式 Agent 架構，而非只有角色名稱、沒有使用流程的聊天機器人。多工具、多模態、長程任務規劃與多 Agent 協作屬於後續可驗證的能力，不是第一版成立的前提。

## 二、背景與問題定義

### 2.1 目標使用者

本計畫服務三類主要使用者：

| 使用者 | 主要需求 | 回答設計重點 |
| --- | --- | --- |
| 糖尿病患者 | 詢問糖尿病藥品與日常照護資訊；整理看診前問題 | 白話說明、來源、可執行的非治療性步驟；不得鼓勵自行停藥、調藥或取代診療 |
| 病患家屬 | 協助理解衛教內容；整理患者已提供的用藥、症狀與時間資訊 | 不替患者推定病史；強調照護界線與必要時尋求醫療協助 |
| 醫護人員 | 查詢 TFDA／指引證據；檢視診前摘要；產生待人工確認的衛教草稿 | 保留來源、日期、適用範圍、證據衝突與未解問題；最終專業判斷由醫護人員負責 |

`declared_role` 目前是使用者自行提供的角色中繼資料（metadata），不是經過驗證的身分，也不能直接作為敏感資料或高風險工具的授權依據。未來的角色感知功能主要用於內容深度、格式與任務流程調整；若涉及權限，仍需獨立的身分驗證（identity verification）與授權控管（authorization）設計。

### 2.2 使用情境篩選依據

本案不從尚未被明確探索的醫療任務開始，而從已有系統性回顧或實際工作流程研究的應用中選擇。這項原則的目的不是宣稱相關技術已經成熟到可以直接上線，而是先挑選「問題已被看見、流程可以描述、成果可以評估」的使用情境，降低提案同時承擔產品探索、臨床驗證與技術研發三種不確定性的風險。

使用情境依下列四項條件篩選：

1. **使用者問題明確**：能說清楚由誰在什麼時點使用，以及系統要協助完成什麼工作。
2. **輸入與輸出可定義**：能建立必要欄位、回答格式、證據來源及完成條件，而不是只要求 Agent「自由回答」。
3. **安全邊界可執行**：能明確列出系統不得進行的診斷、選藥、停換藥及劑量調整，遇到高風險或資料不足時也有可預期的處理方式。
4. **能沿用現有架構**：可由 A 至 E 的政策路由、證據檢索、充分性審核、受限恢復、回答生成及輸出驗證逐步支援，不必先建立完全不同的系統。

| 候選場景 | 既有發展狀況 | 本案決定 | 理由 |
| --- | --- | --- | --- |
| 糖尿病衛教與自我管理支援 | 已有糖尿病專屬系統性回顧；常見功能涵蓋飲食、運動、血糖監測、藥物與併發症資訊 | **納入核心場景** | 與本案糖尿病主題及 RAG 證據架構直接相符 |
| 看診前病史／症狀／用藥資訊收集 | 已有醫療病史蒐集 chatbot 系統性回顧 | **納入核心場景** | 可把 `ASK_USER` 轉成明確產品流程，且不必由 Agent 下診斷 |
| 醫護證據查詢、摘要與衛教草稿 | 醫療對話 Agent 與臨床生成式 AI 已廣泛研究 | **納入核心場景** | 能直接使用 B-approved evidence 與引用驗證能力 |
| 臨床紀錄／ambient scribe | 已形成獨立研究與產品方向 | 暫不優先 | 發展較成熟，但與本案 TFDA 藥品證據主題較遠 |
| 心理健康／CBT 對話 | 有較多隨機試驗與統合分析 | 不納入 | 非本案主題，且需危機與自傷處理體系 |
| 症狀檢查與自動分流 | 已被大量研究，但準確度差異大 | 只保留紅旗警示與轉介 | 不把「有人研究」誤寫成「可自主判斷」 |
| 自主診斷、選藥、停換藥或劑量調整 | 高風險，缺乏足夠的常規使用證據 | **明確排除** | 超出資訊支援定位與目前治理能力 |

三項納入場景在產品中的價值、與 v0.1 的關係及邊界如下：

| 納入場景 | 使用時點與使用者價值 | 與 v0.1 的關係 | 明確邊界 |
| --- | --- | --- | --- |
| 糖尿病衛教與自我管理支援 | 患者或家屬在看診前後，想理解藥品風險、照護資訊或醫護已提供的說明 | 現有 TFDA RAG、B 證據審核、C 回答與 D 輸出驗證可作為第一條基準流程 | 提供一般性、證據導向資訊，不根據個人狀況診斷或更改治療 |
| 看診前資訊收集與整理 | 患者在就醫前整理已知症狀、用藥、發生時間及想詢問醫師的問題，減少現場重複敘述 | v0.1 的 `ASK_USER` 已建立「資料不足時追問」的控制語義；結構化表單、摘要契約與紅旗規則列入 v0.2 | 只整理使用者提供的事實，不補造病史，不輸出診斷或處置建議 |
| 醫護證據查詢與衛教草稿 | 醫護人員需要快速找到來源、查看限制，或準備仍須人工確認的衛教內容 | v0.1 已能保留證據識別碼與執行軌跡；專業版輸出、來源比較與人工確認流程列入 v0.2 以後 | 系統輸出是證據摘要或草稿，不取代醫護人員的專業判斷與最終簽核 |

這三項場景是本提案的**目標產品流程**，不代表 v0.1 已全部完成。v0.1 目前直接交付的是一般藥品風險問題的安全證據流程，以及證據不足時的受限恢復機制；診前資料契約、角色化介面與醫護工作流程將依版本逐步補齊。這樣既能呈現最終用途，也不會把開發藍圖誤報成現成功能。

糖尿病對話 Agent 的研究多集中於飲食、運動、血糖監測、用藥與併發症管理，但高品質試驗及安全升級機制仍不足。因此本案採「支援既有照護計畫」而非「自動制定治療計畫」的定位。

此篩選主要參考[糖尿病對話 Agent 系統性回顧](https://pubmed.ncbi.nlm.nih.gov/40840786/)、[糖尿病自我管理 chatbot 系統性回顧與統合分析](https://pmc.ncbi.nlm.nih.gov/articles/PMC11653048/)、[診前病史蒐集 chatbot 系統性回顧](https://pmc.ncbi.nlm.nih.gov/articles/PMC11393511/)及[症狀檢查器診斷與分流準確度系統性回顧](https://pubmed.ncbi.nlm.nih.gov/37266983/)。這些文獻證明場景已被探索，不代表本系統已取得臨床有效性或安全性證據。

### 2.3 為什麼不能只做 RAG

RAG 適合處理非結構化文件檢索與證據查找，但三類使用者的需求不只包含「從文件找答案」。

| 使用情境 | 單靠 RAG 的限制 | 較適合的能力 |
| --- | --- | --- |
| 查詢藥品商品名、成分與許可證 | 向量搜尋可能回傳近似藥品，難保證精確欄位 | 結構化藥品與許可證查詢工具（Drug／License Lookup Tool） |
| 血糖單位、身體質量指數（BMI）或核准公式計算 | LLM 直接計算可能產生算術或單位錯誤 | 確定性計算工具（Deterministic Calculator Tool） |
| 症狀與緊急風險 | 文件相關不代表已完成安全分流 | 必經紅旗症狀與風險閘門（Mandatory Red-Flag／Risk Gate） |
| 比較不同藥物類別 | 需要對齊比較維度、來源與時間 | 結構化資料、指引檢索與比較功能 |
| 整理就醫資料 | 主要工作是結構化使用者資訊，不一定需要檢索 | 資訊收集、時間軸與轉介摘要工具（Intake／Timeline／Handoff Tool） |
| 醫護證據查詢 | 需要來源版本、日期、衝突與限制 | 證據搜尋與引用驗證工具（Evidence Search／Citation Verification Tool） |

本計畫將 RAG 定位為工具生態中的一項「證據檢索能力」，而不是整個系統的唯一核心。

#### 2.3.1 從固定模組走向受控工具生態

未來將可重複使用、具有明確輸入與輸出的功能封裝成工具，提供 Agent 在允許的任務與階段中呼叫。這個方向能讓系統在不重寫整條流程的情況下加入新資料來源或能力，也能分別測試每個工具的正確率、延遲、錯誤及版本。

預計工具化的能力包括：

- `EvidenceRetrievalTool`：依來源、查詢詞及篩選條件回傳候選證據。
- `DrugLicenseLookupTool`：以藥品名稱、成分或許可證識別碼進行精確查詢。
- `GuidelineRetrievalTool`：查找具有版本、日期與適用範圍的核准指引內容。
- `PreVisitIntakeTool`：依資料契約收集並整理使用者已提供的診前資訊。
- `DeterministicCalculatorTool`：執行通過審核的公式、單位轉換或量表計算。
- `EvidenceComparisonTool`：以固定維度整理跨來源證據及保留衝突，不自行決定治療方案。

工具化將分階段進行，而不是在 v0.1 直接開放 Agent 自由呼叫：

| 版本 | Agent 與工具的關係 | 主要控制方式 |
| --- | --- | --- |
| v0.1 | RAG 由固定工作流程呼叫；Agent 只有 `ASK_USER`、`REWRITE_QUERY`、`FALLBACK` | 固定圖路由、步數限制、失敗即安全終止 |
| v0.2 | 建立 `ToolRequest`、`ToolResult`、工具登錄表與執行器；工具仍主要由流程指定 | 資料格式驗證、允許清單、逾時與執行軌跡 |
| v0.3 | Planner 在特定任務中增加受限 `CALL_TOOL` | 任務權限、參數驗證、成本／次數限制及結果回到 B 審核 |
| v1.0 | 在身分、隱私、監控及人工審查完成後進行受控試用 | 最小權限、版本治理、事件處理及停用機制 |

並非所有模組都應成為 Agent 可以選擇的工具。A、B、D 是必經安全閘門；C 是正式回答生成器；E、狀態、稽核與隱私控制屬於系統基礎設施。這些元件必須由工作流程固定執行，Agent 不能跳過、關閉或推翻。任何工具結果也只算候選觀察或候選證據，必須重新通過 B，再經 C 與 D，才能成為對外回答。

### 2.4 核心問題

本計畫欲解決以下問題：

1. 如何讓不同角色取得適合其需求與理解程度的糖尿病資訊？
2. 如何整合非結構化檢索、結構化資料與確定性計算，而不把所有工作交給單一大型語言模型（Large Language Model, LLM）？
3. 如何允許 Agent 分解任務與選擇工具，同時保留政策、證據與輸出安全邊界？
4. 如何保存每次工具選擇、證據來源、系統限制與最終決策，使結果可重現、可評估、可稽核？

### 2.5 資料來源評選原則

本版提案不預先指定正式資料集。後續應先完成資料來源盤點與評選，再決定哪些來源可進入原型（prototype）、評估（evaluation）與正式服務。評選面向至少包括：

- 權威性與發布單位。
- 糖尿病任務與目標使用者的涵蓋範圍。
- 資料授權、使用限制與可否對外提供衍生內容。
- 更新頻率、版本管理與過期資料處理方式。
- 是否具備穩定識別碼（identifier）、來源日期與可追溯中繼資料（metadata）。
- 結構化程度、文件品質、重複、衝突與缺漏情形。
- 是否涉及個人資料、敏感資料或其他隱私風險。
- 是否能建立具代表性的訓練、開發與獨立評估集合。

後文所稱「權威證據來源」皆為待評選能力類型，不代表已指定特定機構、資料庫或語料庫（corpus）。

## 三、目前基礎與成熟度

目前專案已具備以下內部基礎流程。為方便外部閱讀，以下使用功能名稱，不使用團隊內部模組代號：

```text
使用者
→ 輸入安全與任務路由
→ 檢索問題準備
→ 證據檢索
→ 證據與脈絡充分性審核
→ 證據導向回答生成
→ 最終輸出安全驗證
→ 正式回答／安全替代回應（fallback）

可觀測性與評估紀錄橫跨全部階段。

證據不足時，可進入受限恢復流程：
ASK_USER／REWRITE_QUERY／FALLBACK
```

### 3.1 已建立的能力

- 輸入安全與任務路由：請求資料格式（request schema）、角色／意圖訊號、提示注入防護（prompt injection guard）與確定性政策路由。
- 檢索問題準備：保留原始問題（original query）的可替換資料契約；目前基準版本採原句檢索（identity expansion）。
- 證據檢索：可替換的檢索器介面（retriever interface）與標準化證據資料契約；目前原型使用 129 筆 TFDA 藥品風險溝通資料，正式服務的來源組合、更新及失效政策仍待評選。
- 證據與脈絡審核：脈絡充分性資料契約（context sufficiency contract）與證據批准邊界。
- 受限恢復 Agent v0.1：`ASK_USER`、`REWRITE_QUERY`、`FALLBACK` 三種受限恢復動作。
- 證據導向回答生成：證據導向回答、已支持主張（supported claims）、未支持需求（unsupported requests）與限制說明（limitations）資料契約。
- 最終輸出安全驗證：必經輸出閘門、證據識別碼與政策驗證。
- 可觀測性：結構化執行軌跡（trace）、延遲、失敗、評估紀錄與人類可讀執行路徑。
- LangGraph 工作流程：固定路由、Agent 次數限制、請求與實際執行動作紀錄，以及失敗即安全終止（fail-closed）的替代回應。

### 3.2 目前限制

- 系統仍是展示版本（demo）、最小可行產品（Minimum Viable Product, MVP）與研究基準，不是自主臨床決策系統。
- 現有檢索原型可執行，但正式資料來源尚未選定；證據審核、回答生成與輸出驗證的部分語意元件仍包含測試替身（fixture）或展示用實作。
- 急症或緊急風險門檻尚未完成正式臨床驗證。
- `declared_role` 尚未連結身分驗證與授權控管（authorization）。
- 尚未建立正式環境的受保護健康資訊（Protected Health Information, PHI）、資料保存、存取控制與持久化對話政策。
- Agent 尚不能動態選擇一般工具；目前只處理證據不足後的有限恢復。

本提案將上述現況視為後續發展基線，避免把測試替身結果或少量展示用執行軌跡誤解為臨床可用性證據。

## 四、計畫定位與目標

### 4.1 計畫定位

本計畫定位為：

> 建立一套角色感知（role-aware）、證據導向（evidence-grounded），支援糖尿病衛教、診前資訊整理及醫護證據工作的對話式 Agent。

它不是：

- 自動診斷系統。
- 自動開藥、停藥或調整劑量系統。
- 未經醫護審核即可執行臨床處置的 Agent。
- 只根據 LLM 內部知識回答的通用聊天機器人。
- 只將文件放入向量資料庫的單一 RAG 聊天機器人。

### 4.2 計畫目標

1. 建立患者、家屬與醫護人員的角色—任務—回答政策矩陣（role-task-response policy matrix）。
2. 以現有 A／Query Expansion／RAG／B／Agent／C／D／E 流程支援三條核心使用流程。
3. 將 `ASK_USER` 用於診前資訊補充，將 `REWRITE_QUERY` 用於證據檢索恢復，將 `FALLBACK` 用於證據不足或超出範圍時安全終止。
4. 建立診前資訊摘要與醫護證據摘要的結構化輸出契約。
5. 確保所有證據結果均通過證據充分性與來源審核，所有正式回答均通過最終輸出安全驗證。
6. 在核心流程通過評測後，再逐步建立工具登錄表、受控工具執行器及多來源能力。
7. 建立角色、任務、證據、Agent 動作、延遲、錯誤及終止原因的完整執行軌跡與評估方法。

### 5.1 現有架構與產品任務的對應

| 現有元件 | 在產品中的責任 | 對三條使用流程的作用 |
| --- | --- | --- |
| A：Input Router／Policy Gate | 判斷角色、任務、風險與是否可進入一般流程 | 阻擋診斷、調藥、提示注入；辨識衛教、診前整理或醫護證據任務 |
| Query Expansion | 保存原始問題並準備檢索問題 | 將口語藥名或描述轉成不改變原意的檢索查詢 |
| RAG | 回傳候選證據，不直接回答 | 檢索 TFDA 藥品風險資料；後續可擴充核准指引來源 |
| B：Context／Evidence Gate | 判斷證據及必要情境是否足夠 | 決定可回答、需補問、需人工審查或安全退回 |
| Agent Planner／Rewriter | 僅處理證據不足後的恢復 | `ASK_USER` 補最小必要資訊；`REWRITE_QUERY` 改善檢索；`FALLBACK` 終止 |
| C：Evidence-aware Generator | 只使用核准證據產生任務化輸出 | 產生衛教回答、診前摘要或醫護端證據草稿 |
| D：Output Gate | 檢查引用、禁用內容與角色適切性 | 防止無證據主張、個人化調藥指令及錯誤角色輸出 |
| E：Observability | 保存路由、證據、動作、輸出與終止原因 | 支援跨組除錯、醫療審閱及版本比較 |

各元件的輸入、輸出與控制邊界可進一步整理如下：

| 元件 | 主要輸入 | 主要輸出 | 不可執行的行為 |
| --- | --- | --- | --- |
| A | 原始問題、宣告角色、會話中繼資料 | 任務類型、政策結果、風險與允許的下一步 | 不根據檢索結果回答，也不授權 Agent 跳過風險規則 |
| Query Expansion | 原始問題、允許的任務資訊 | 保留原意的檢索問題 | 不添加使用者未提供的病史、藥名或診斷 |
| RAG／資料工具 | 結構化工具參數或檢索問題 | 候選證據、來源、日期、分數與錯誤 | 不直接形成正式醫療回答，也不自行批准證據 |
| B | 候選證據、任務必要資訊、來源中繼資料 | `PASS`、`INSUFFICIENT`、`REVIEW` 或 `UNSAFE` | 不生成答案，也不因 Agent 偏好降低證據門檻 |
| Agent Planner | B 的不足原因、允許動作及剩餘步數 | `ASK_USER`、`REWRITE_QUERY`、`FALLBACK`；未來才有受限 `CALL_TOOL` | 不直接回答、不改變 Gate 結果、不執行未登錄工具 |
| C | B 核准的證據、角色與任務輸出契約 | 有來源、揭露限制的候選回答或摘要 | 不使用未核准證據，不自行補造患者資訊 |
| D | 候選回答、引用、角色與政策結果 | `PASS` 或安全替代回應 | 不放行無來源主張、診斷或個人化調藥指令 |
| E | 全流程事件、版本、延遲與錯誤 | 可稽核執行軌跡與評估資料 | 不修改流程狀態或醫療決策 |

### 5.2 v0.1 的 Agent 控制範圍

v0.1 的 Agent 不是可任意規劃任務的通用 Agent，而是證據不足後的**受限恢復控制器**。其控制規則如下：

- 只有 B 回傳 `INSUFFICIENT` 才能啟動 Agent；A 已封鎖或 B 判定 `UNSAFE` 的請求不能交由 Agent 繞回。
- `ASK_USER` 只詢問完成任務所需的最小資訊，並結束當次執行；使用者補充後建立新 request，重新由 A 檢查。
- `REWRITE_QUERY` 只能改善搜尋表述，不能改變原始問題意圖；改寫後必須重新經過 RAG 與 B。
- `FALLBACK` 在超出範圍、嘗試次數用盡或仍無足夠證據時安全終止。
- v0.1 最多兩個 Agent 步驟，且改寫與澄清次數各受限制，避免無限循環與不可預期行為。
- v0.1 沒有一般性的 `CALL_TOOL`；此能力必須等工具契約、執行器、允許清單與評測完成後才加入。

### 5.3 能力與權責分類

| 類型 | 元件 | Agent 是否可選擇 | 說明 |
| --- | --- | --- | --- |
| 工具（Tool） | 證據檢索、藥品查詢、指引搜尋、計算、資訊收集 | 是，但須通過允許清單與執行階段限制 | 可選能力；未呼叫時能力下降，但不能破壞安全性 |
| 閘門（Gate） | 輸入政策、必經風險篩檢、證據批准、最終輸出驗證 | 否 | 必經信任邊界；Agent 不能跳過或推翻 |
| 生成器（Generator） | 角色適配回答生成 | 否，正式回答流程固定進入 | 只能使用已批准證據（approved evidence） |
| 基礎設施（Infrastructure） | 工具執行器、狀態、記憶、執行軌跡、隱私控制 | 否 | 系統擁有，不由 LLM 控制 |

### 5.4 RAG 工具設計原則

第一個工具建議將現有檢索器介面包裝為資料來源中立的：

```text
EvidenceRetrievalTool(source_id, query, filters)
→ 執行狀態（status）
→ 檢索問題（retrieval_queries）
→ 候選證據（candidate evidence[]）
→ 來源／日期／分數／中繼資料
→ 延遲／錯誤
```

不建議第一版採用：

```text
RAGTool(question)
→ 最終醫療回答
```

因為檢索工具直接產生正式答案，容易混合證據搜尋、證據批准與回答生成，並可能繞過證據審核、回答生成及最終輸出驗證的既有邊界。

### 5.5 未來 Tool Call 在架構中的位置

未來不是以新的 Agent 架構取代 v0.1，而是在既有 A、B、C、D、E 安全骨架中，逐步擴充 Agent 可以選擇的工具：

```text
v0.1｜固定流程呼叫 RAG
  A → Query Expansion → RAG → B → 受限恢復／C → D
                         │
                         └── Agent 只有 ASK_USER／REWRITE_QUERY／FALLBACK

v0.2｜先建立工具契約與受控執行器
  工作流程 → Tool Registry → Tool Executor → 候選 observation／evidence → B
                    └── 由系統指定工具，先驗證介面、錯誤與追蹤

v0.3｜再開放受限 CALL_TOOL
  B 資料不足 → Agent Planner → CALL_TOOL（只限允許清單）
                                  │
                                  ▼
                         Tool Executor → ToolResult → B 再次審核
```

這個演進順序保留兩項重要原則：第一，工具只擴充 Agent 的取得資料與處理能力，不擴充其安全權限；第二，新增任何工具都不應形成繞過 B、C 或 D 的答案捷徑。如此才能把模組化帶來的擴充性，與醫療情境要求的可控性放在同一個架構中。

## 六、優先使用情境與實際流程

| 優先度 | 使用情境 | 主要對象 | 所需能力 | 安全要求 |
| --- | --- | --- | --- | --- |
| P0 | 糖尿病藥物風險與衛教查詢 | 患者、家屬 | 現有 A／RAG／B／C／D | 證據來源與充分性審核；不得診斷或調藥 |
| P0 | 資訊不足時追問與問題改寫 | 三類角色 | 現有受限 Planner／Rewriter | 不得猜測藥名、症狀、病史或診斷 |
| P0 | 醫護證據查詢與待確認衛教草稿 | 醫護人員 | RAG、B-approved evidence、專業版 C output | 顯示來源、日期、限制與證據缺口；人工確認後使用 |
| P1 | 看診前症狀、用藥與問題整理 | 患者、家屬、醫護人員 | `ASK_USER`、結構化 intake schema、摘要輸出 | 不補造資料；紅旗訊號固定轉介；摘要不是診斷 |
| P1 | 商品名、成分、類別與許可證查詢 | 三類角色 | 未來結構化藥品／許可證工具 | 精確識別碼、來源日期、避免近似藥品誤配 |
| P2 | 專業指引與跨來源證據比較 | 醫護人員 | 未來指引來源與證據比較 | 固定比較維度、版本與衝突保留；不可自動選藥 |
| P3 | 多輪追蹤、附件與多模態資料 | 三類角色 | 持久化狀態、文件／影像輸入、人工審查 | PHI、同意、權限、保存期限及專科評測通過後才啟用 |

### 6.1 患者／家屬衛教流程

```text
提出糖尿病藥品或照護問題
→ A 排除急症、診斷及調藥要求
→ RAG 檢索 TFDA／核准來源
→ B 判斷證據是否足以回答
→ 不足時詢問藥品名稱或最小必要背景
→ C 產生白話、有來源且揭露限制的回答
→ D 檢查後輸出或安全退回
```

### 6.2 看診前資訊整理流程

```text
患者選擇「準備看診」
→ 系統依結構化欄位詢問已知藥品、發生時間、症狀描述及想問醫師的問題
→ A 在每次補充資訊後重新檢查風險
→ 紅旗訊號走固定轉介，不由 Planner 自行決定是否就醫
→ C 只整理使用者已提供的內容
→ D 檢查是否出現診斷、推測病史或治療指令
→ 輸出可供患者攜帶、醫護快速閱讀的摘要
```

### 6.3 醫護證據工作流程

```text
醫護提出藥品風險或衛教主題
→ RAG 檢索具版本與來源的證據
→ B 保留足夠、相關且無未處理衝突的證據
→ C 產生證據摘要與待確認衛教草稿
→ D 驗證引用、限制與禁止內容
→ 醫護人員檢視、修改並負責最終使用
```

三條流程共用同一套安全骨架，但輸出資料契約不同。這比建立三個彼此獨立的 chatbot 更容易維護，也能讓同一份證據在不同角色介面中維持事實一致。

## 七、分期建置與驗收

正式日期仍需依人力與經費確認。以下先提供版本與工作階段的對應，避免把最終藍圖誤認為 v0.1 已完成能力。工期是假設至少有一名 LLM／Agent 工程師、一名 RAG／資料工程師、兼任 QA，以及可定期參與的醫療／藥事審閱者所做的初估。

| 版本 | 對應階段 | 主要成果 | 初估開發期 | 是否為目前能力 |
| --- | --- | --- | ---: | --- |
| v0.1｜安全與證據基線 | 階段 0 | A 至 E、TFDA RAG、B insufficient 後的 `ASK_USER`／`REWRITE_QUERY`／`FALLBACK` | 剩餘收斂約 3–4 週 | **已有主要程式骨架**，仍需正式語意元件與擴大評測 |
| v0.2｜三流程 MVP | 階段 1、2 | 患者衛教、診前資訊整理、醫護證據草稿；角色與任務輸出契約 | 約 6–8 週 | 尚未完成 |

### 階段 0／v0.1｜現有安全基線收斂

**目的**：凍結目前輸入路由、檢索、證據審核、回答生成、輸出驗證、可觀測性與 Agent v0.1 資料契約，作為後續比較基準。

主要工作：

- 標示真實元件、測試替身（fixture）、展示版本（demo）與尚未驗證的語意元件。
- 完成候選資料來源盤點、授權與更新機制比較；本階段不預設最終資料集。
- 固定目前請求、證據、Agent 決策、回答與輸出驗證結果，以及執行軌跡資料格式。
- 建立基準正確率、安全替代回應率、延遲與失敗樣態。

驗收條件：

- 現有資料契約測試通過。
- 主要 `ASK_USER`、`REWRITE_QUERY`、`FALLBACK` 執行軌跡可重現。
- 文件與實際原始碼、測試一致。

### 階段 1／v0.2-A｜RAG 工具化與工具基礎設施

**目的**：建立未來所有工具共用的標準，不立即擴大 LLM 控制權。

主要工作：

- `ToolRequest`、`ToolResult`、`ToolError` 與 `CanonicalObservation/Evidence` 資料格式（schema）。
- 資料來源中立的 `EvidenceRetrievalTool` 轉接器（adapter）。
- 工具登錄表、執行器、允許清單、逾時控制與執行軌跡。
- 仍由工作流程圖以確定性方式呼叫指定的測試檢索來源。

驗收條件：

- 工具參數與結果均通過資料格式驗證。
- 所有證據保留識別碼、來源、日期與中繼資料。
- 工具錯誤不會繞過證據審核、回答生成與最終輸出驗證，並能提供安全替代回應。
- 包裝前後的基準案例結果無非預期退步。

### 階段 2／v0.2-B｜三條角色與任務流程產品化

**目的**：從「文件問答」擴展為可展示患者衛教、診前資訊整理與醫護證據工作的糖尿病資訊支援服務。

主要工作：

- 建立角色—任務—回答政策矩陣。
- 建立任務分類體系（task taxonomy）與測試資料。
- 建立患者衛教、診前摘要與醫護證據草稿三種輸出資料契約。
- 建立三條流程各自的 happy path、資訊不足、證據不足與高風險案例。
- 加入第一個結構化藥品／許可證工具。
- 加入結構化資訊收集／時間軸工具。
- 規劃必經風險篩檢資料契約；臨床門檻需另行審核。

驗收條件：

- 同一證據可依角色產生不同深度、但事實一致的輸出。
- 三條核心流程均有可重現的端到端案例及人工審閱結果。
- 使用者自行聲明的角色不會自動提升資料或工具權限。
- 結構化查詢以精確識別碼回傳，不使用相似文件猜測藥品。
- 患者／家屬輸出不包含自行停藥、調藥或取代診療的指示。

### 階段 3／v0.3｜受限多工具協調器

**目的**：讓規劃器（Planner）能在有限動作空間中選擇核准工具。

主要工作：

- Agent 動作擴充為 `CALL_TOOL`。
- 建立工具允許清單、參數驗證、步數／成本／逾時限制。
- 建立重複呼叫偵測（duplicate-call detection）與應用程式掌控的快取政策。
- 所有證據工具結果強制重回證據與脈絡充分性審核。
- 記錄模型請求動作與系統實際執行動作。

驗收條件：

- Agent 不能呼叫未註冊工具或修改限制值。
- 非法工具名稱或參數會失敗即安全終止。
- 超過步數、工具或成本限制時安全終止。
- Agent 不能批准自己的工具結果，也不能繞過最終輸出安全驗證。
- 工具選擇正確率與不必要工具呼叫率可量測。

### 階段 4／v1.0｜持久化、人工審查與受控試用準備

**目的**：支援可治理的多輪互動與正式環境需求。

主要工作：

- 澄清問題檢查點（clarification checkpoint）與重新進入政策。
- 結構化短期狀態，而非只保存完整聊天文字。
- PHI 遮蔽、加密、保存、刪除與存取控制。
- 人工審查與臨床升級處理路徑。
- 正式環境監控、版本管理與回復機制（rollback）。

驗收條件：

- 不同對話識別碼（thread）／使用者資料明確隔離。
- 使用者補充資料後重新通過必要的輸入政策與風險邊界。
- 可追蹤回答所使用的模型、提示詞、工具、資料版本與證據。
- 人工審查與異常事件具有完整稽核軌跡（audit trail）。

### 7.1 多模態、長程規劃與多 Agent 的位置

這三項技術保留在目標研究架構中，但必須由使用情境觸發，不作為提案的裝飾性元件：

| 研究能力 | 只有在什麼需求成立時加入 | 加入前的必要條件 |
| --- | --- | --- |
| Multimodal Reasoning | 使用者需要上傳藥袋、藥品標示、血糖紀錄或其他核准附件，且純文字無法完成任務 | 影像／文件品質檢查、敏感資料政策、模態專屬測試與人工覆核 |
| Long-horizon Planning | 需要跨多輪完成診前資料收集、缺漏補充、證據查詢與摘要，而非單次問答 | 明確任務狀態、最大步數、可中止／恢復、PHI 保存與失敗回復 |
| Multi-agent Boundary Supervision | 單一 Planner 加固定 Gate 的基準評測顯示不足，且第二個 Agent 能處理明確、獨立的審查任務 | 與單 Agent 基準比較、權責不重疊、不能用 Agent 共識取代醫療證據或固定 Gate |

因此，最終架構可以容納這些能力，但 v0.2 的成敗仍以三條核心使用流程能否安全完成來判定。若沒有量測到額外效益，就不因技術名稱而升級架構複雜度。

## 八、評估與驗收指標

正式數值目標應在階段 0 基準評估完成後確認。本版先定義必須量測的指標。

### 8.1 任務與回答品質

- 意圖／任務分類正確率。
- `ASK_USER`、`REWRITE_QUERY`、`CALL_TOOL`、`FALLBACK` 動作適切率。
- 患者／病患家屬／醫護人員回答適切率。
- 已支持主張比例與未支持主張比例。
- 引用精確率、來源與日期完整率。
- 證據衝突揭露率。

### 8.2 工具品質

- 工具選擇正確率。
- 工具參數資料格式有效率。
- 檢索召回率與排序品質。
- 結構化查詢精確匹配率。
- 不必要工具呼叫率與重複呼叫率。
- 工具錯誤恢復與逾時處理表現。

### 8.3 安全與控制

- 輸入政策邊界被繞過：目標為 0。
- 未經證據審核批准的證據進入正式回答生成：目標為 0。
- 未經最終輸出安全驗證通過的候選回答對外輸出：目標為 0。
- 未註冊工具執行：目標為 0。
- 超限後仍繼續執行：目標為 0。
- 高風險或不確定案例的安全替代回應／人工審查適切率。

### 8.4 效能與營運

- 端到端延遲與各元件延遲。
- 權杖用量（token）、應用程式介面（API）、圖形處理器（GPU）與每次請求成本。
- 工具成功、空結果與錯誤率。
- 快取命中率。
- 執行軌跡完整率。
- 模型、提示詞、工具與資料版本可重現性。

## 九、風險與治理原則

| 風險 | 說明 | 初步控制方式 |
| --- | --- | --- |
| LLM 過度自主 | 同一模型同時選工具、批准證據及回答，可能放大錯誤 | 決策與執行分離；輸入政策、證據審核與輸出驗證採固定邊界 |
| 工具結果錯誤或衝突 | 專用工具仍可能出錯，不同來源可能矛盾 | 結果視為觀察資料；保留來源脈絡（provenance）；由獨立證據驗證器仲裁或轉人工 |
| 錯誤藥物辨識 | 近似商品名或檢索候選被誤認為使用者實際用藥 | 精確識別碼；必要時 `ASK_USER`；不得由前幾筆檢索結果猜測 |
| 無限循環與成本失控 | Agent 重複改寫或呼叫高成本工具 | 步數、單一工具、總執行時間、token 與成本限制 |
| 緊急症狀漏判 | Agent 未主動選擇分流工具 | 高風險篩檢設為必經閘門，不作為普通可選工具 |
| 身分與權限混淆 | 使用者自稱醫護人員不代表已驗證 | 角色適配與授權控管分離 |
| PHI 與隱私 | 訊息、執行軌跡、附件可能含敏感資料 | 資料最小化、遮蔽、加密、保存期限與存取控制 |
| 測試替身被誤認正式成果 | 資料契約測試通過不代表臨床語意表現 | 報告明確標示真實／測試替身／展示元件；分開評估 |

## 十、預期成果

1. 一套具版本管理、支援三條核心使用流程的糖尿病對話式 Agent 參考架構。
2. 統一工具軟體開發套件（SDK）、資料契約、登錄表與受控執行器。
3. 資料來源可替換的證據檢索工具與至少一項非 RAG 能力之示範實作。
4. 三類角色的任務、回答與安全政策矩陣。
5. 受限工具選擇 Agent 與 LangGraph 工作流程。
6. 證據帳本、必經證據／輸出邊界與完整結構化執行軌跡。
7. 離線迴歸、工具資料契約、對抗式安全與角色適配測試集。
8. 真實、測試替身、展示與正式環境準備度的元件矩陣及技術報告。

## 十一、待確認事項

正式提案書下一版需補齊：

1. 提案對象與正式格式。
2. 計畫執行單位、主持人與協作角色。
3. 總期程、各階段人月與預算上限。
4. 第一階段只建立資料來源中立的檢索工具資料契約，或同時納入藥品／許可證工具。
5. 可使用的正式資料來源及其授權、更新頻率與版本政策。
6. 是否納入醫護專家進行風險門檻、回答政策與評估審查。
7. 是否處理個人資料、檢驗值、處方、附件或其他 PHI。
8. 預期部署環境：研究展示、內部系統、公開服務或臨床場域。
9. v0.2 是否同時開發三條核心流程，或先以患者衛教與醫護證據工作為第一批、診前整理為第二批。
10. 正式關鍵績效指標（Key Performance Indicator, KPI）、驗收樣本數與人工評估流程。

## 十二、結論

本計畫的核心不是單純增加更多模型或把所有功能包成工具，而是讓患者衛教、診前資訊整理與醫護證據工作共用一套清楚區分 **可選能力** 與 **強制安全邊界** 的 Agent 平台。RAG、藥物資料庫、指引檢索、計算與資訊整理可以逐步標準化為工具；政策路由、緊急風險檢查、證據批准與最終輸出驗證則必須由系統固定執行。

透過「安全基線 → RAG 工具化 → 角色與多來源能力 → 受限多工具協調 → 持久化記憶與服務化」的分期方法，本計畫可以在每一階段取得可展示、可測試、可驗收的成果，同時降低一次導入完整自主 Agent 所帶來的醫療安全、成本與治理風險。
