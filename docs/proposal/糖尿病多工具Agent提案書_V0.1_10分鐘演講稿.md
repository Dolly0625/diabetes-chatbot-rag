# 糖尿病多工具 Agent 提案書 V0.1｜10 分鐘演講稿

> 搭配文件：[糖尿病多工具Agent提案書_V0.1.md](./糖尿病多工具Agent提案書_V0.1.md)  
> 報告重點：使用場景、目標架構、實際流程、版本與時程

## 0:00–0:35｜開場

各位好，今天我要報告的是「角色感知、證據導向之糖尿病對話式人工智慧代理系統建置提案」。

這份 v0.1 文件整理了我們目前的技術基礎、建議的目標架構，以及後續開發階段。今天主要說明四件事：這個 Agent 給誰使用、使用場景是什麼、架構為什麼這樣設計，以及 v0.1 到 v1.0 分別要完成什麼。

## 0:35–2:15｜第一、二章：使用者與使用情境

> 畫面停在「一、計畫摘要」，再捲到「2.1 目標使用者」。

這個系統主要服務糖尿病患者、病患家屬與醫護人員，我們先聚焦三個能互相連接的使用情境。

第一個是患者與家屬的糖尿病衛教。例如患者想了解藥品用途、注意事項，或近期有沒有 TFDA 風險通知；家屬也可能希望把原本較難理解的衛教內容轉成白話說明。系統會先確認問題範圍，再從核准來源搜尋證據。如果沒有藥名就進一步詢問，不能自行猜測。這個場景只協助理解資訊，不會替患者停藥、換藥或調整劑量。

第二個是患者的看診前資訊整理。Agent 依照固定欄位，詢問患者已知的藥品名稱、症狀、發生時間，以及最想詢問醫師的問題，最後把患者實際提供的內容整理成結構化摘要。系統不補造病史，也不產生診斷；若出現預先定義的高風險訊號，就進入固定轉介流程。

第三個是醫護人員檢視診前摘要。醫護看到的不是整段聊天紀錄，而是患者目前用藥、症狀時間、主要問題、資料缺漏及需要優先確認事項。未來若需要確認藥品或查找證據，可以再呼叫相應工具。系統只整理與標示，不替醫護人員決定診斷或治療。

所以這三個場景形成一條完整流程：患者與家屬先理解資訊，患者在看診前整理狀況，醫護人員再檢視摘要並進行確認。

## 2:15–2:55｜第二章：為什麼不能只做 RAG

> 畫面捲到「2.3 為什麼不能只做 RAG」。

RAG 適合搜尋 TFDA 風險通知或指引文件，但不是所有任務都適合用文件相似度處理。

例如確認商品名、成分或許可證，需要精確的結構化藥品資料庫；單位轉換或公式應交給確定性計算工具；診前摘要則需要結構化資訊收集工具。因此，RAG 是未來工具生態中的一項證據檢索能力，不是整個系統的全部。

## 2:55–3:30｜第三章：目前基礎

> 畫面捲到「三、目前基礎與成熟度」。

目前我們已經建立從輸入安全、RAG、證據充分性審核、回答生成到輸出驗證的基本流程。證據不足時，Agent 可以選擇 `ASK_USER`、`REWRITE_QUERY` 或 `FALLBACK`。

不過，目前仍是研究原型，部分語意元件是 fixture 或展示實作，PHI、正式身分授權及臨床驗證也尚未完成。因此，現在證明的是架構與控制流程可以執行，不是已經能直接投入臨床使用。

## 3:30–6:45｜第五章：建議目標架構

> 畫面捲到「五、建議目標架構」，停在架構圖。這是報告重點。

接下來這張圖是整份提案的核心。

最上方是三個產品入口：患者與家屬的衛教、患者的看診前資訊整理，以及醫護人員的證據與摘要工作。三個入口的目的不同，但共用同一套安全架構。

首先是 A，也就是輸入安全、任務與風險路由。A 會判斷使用者想完成什麼，以及是否涉及高風險、診斷或調藥。如果超出範圍，系統就提供安全替代回應或真人醫療協助；允許的任務才繼續往下。

接著是 Query Expansion 和 RAG。Query Expansion 把口語問題整理成適合搜尋的查詢，但不能改變原意或加入使用者沒提供的病史。RAG 或核准資料工具只回傳候選證據，不直接產生醫療回答。

檢索結果接著進入 B，也就是證據與脈絡充分性閘門。B 會判斷證據是否相關、來源是否足夠，以及目前資訊能不能完成任務。

如果 B 判定 `PASS`，才能進入 C 生成內容；如果是 `INSUFFICIENT`，才會啟動受限 Agent；如果內容不安全或需要審查，就轉人工或安全停止。

中間的 Agent Planner 是 v0.1 真正有 Agent 決策的位置，但它目前不是能自由規劃所有任務的通用 Agent，而是證據不足後的受限恢復控制器。

它只有三個動作。`ASK_USER` 是請使用者補充最小必要資訊，補充後重新從 A 進入；`REWRITE_QUERY` 是不改變原意地調整搜尋方式，再重新經過 RAG 和 B；`FALLBACK` 則是在嘗試次數用盡或仍缺乏證據時安全停止。

當 B 判定資料充分後，C 才能依角色和任務生成內容。患者端可能是白話衛教，診前任務可能是結構化摘要，醫護端則是待確認的摘要或證據內容。C 只能使用 B 已核准的證據，不能自行補充沒有來源支持的主張。

C 產生的內容還要經過 D。D 會檢查引用、角色適切性、證據範圍，以及是否出現診斷或個人化調藥建議。只有 D 通過，內容才正式輸出。

最後的 E 橫跨整條流程，記錄任務路由、使用證據、Agent 動作、輸出與終止原因，讓系統可以追蹤、評估和重現，但 E 不會更改任何安全判斷。

這張圖最重要的原則是：Agent 可以選擇部分能力，但不能選擇是否遵守安全規則。未來 Agent 可以呼叫 RAG、藥品資料庫或計算工具，但 A、B、D 這些安全閘門必須固定執行，不能被 Agent 跳過。

## 6:45–7:40｜第六章：案例流程

> 畫面捲到「六、優先使用情境與實際流程」。

這裡用患者準備看診的例子，把前面的架構串起來。

假設患者表示服藥後有些不舒服，而且準備回診。A 先檢查是否有高風險訊號；若屬於一般診前整理，系統就詢問藥品名稱、症狀、發生時間和想問醫師的問題。資料不完整時，Agent 會追問，不能自行猜測。

收集完成後，C 只整理患者實際提供的內容，D 再檢查有沒有推測病史、診斷或治療指令。醫護人員看診前便能看到主要問題、資料缺漏與需要優先確認的事項；必要時再透過工具查證藥品或相關證據。

這個案例顯示，Agent 的價值不只是回答問題，而是發現資訊不足、要求補充，並把資料整理成下一位使用者可以採用的形式。

## 7:40–9:15｜第七章：版本與時程

> 畫面捲到「七、分期建置與驗收」。

我們不會一次做到完整的自主 Agent，而是逐步增加能力。

v0.1 是先把安全與證據流程建立好，確認問題如何進入、如何搜尋、如何審核，以及回答前要經過哪些檢查。重點不是功能很多，而是證明整條流程跑得動、可以追蹤，而且資料不足時不會勉強回答。

v0.2 是把架構變成可展示的產品流程，完成患者衛教、看診前整理與醫護檢視摘要。同時把 RAG、藥品查詢及資訊整理包裝成具有統一輸入輸出的工具，但這時主要仍由系統決定何時使用。

v0.3 才加入受限的 `CALL_TOOL`，讓 Agent 根據任務選擇允許清單內的工具。例如一般證據問題使用 RAG，精確確認藥品時使用結構化資料庫。工具結果仍須回到 B 審核，不能直接成為答案。

v1.0 則補上持久化對話、PHI、身分與權限、人工審查、監控及錯誤回復，讓系統具備受控試用的準備度。

從目前收斂到 v1.0，初估需要二十七到三十六週。這是系統開發與受控試用準備時程，不代表已完成臨床驗證或醫療核准。

## 9:15–10:00｜第十二章：結論

> 直接捲到「十二、結論」。

最後總結。

這個提案不是要做一個自行看病或決定治療方式的 AI，而是建立一套面向糖尿病患者、家屬與醫護人員，具有明確使用流程、證據來源與安全邊界的對話式 Agent。

現階段先收斂 v0.1 的安全與證據基線；v0.2 完成三個實際場景，並把能力逐步工具化；v0.3 才讓 Agent 在限制下自行選擇工具；最後再補齊正式環境需要的隱私與治理。

整套架構最核心的原則是：工具可以增加 Agent 的能力，但不能增加 Agent 的安全權限。

以上是這次的提案報告，謝謝大家。

## 時間不足時的刪減順序

如果現場時間少於 10 分鐘，依序刪減：

1. 第三章縮成一句「目前已有可執行基線，但仍是研究原型」。
2. 「為什麼不能只做 RAG」只保留藥品資料庫的例子。
3. 第六章案例縮成兩句，但不要刪除第五章架構圖。

無論時間多短，都要保留三個訊息：

1. 系統串起患者衛教、診前整理與醫護檢視摘要。
2. Agent 可以選擇能力，但不能跳過 A、B、D。
3. v0.1 是安全基線；受限多工具 `CALL_TOOL` 在 v0.3。
