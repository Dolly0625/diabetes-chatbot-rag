## 一、計畫摘要

本計畫擬建置一套面向 **糖尿病患者、病患家屬及醫護人員** 的角色感知、證據導向之糖尿病資訊與安全支援人工智慧代理系統（Agent）。最終產品聚焦四項任務：**糖尿病衛教與自我管理支援、看診前資訊收集與整理、處方／藥袋辨識與仿單衛教、醫護端證據查詢與衛教草稿**。其中前三條文字流程先於 v0.2 驗證；需要 OCR、藥品唯一匹配與使用者確認的處方／藥袋流程列入 v0.4。系統不自行診斷或調整治療，而以輸入政策、證據充分性與最終輸出三道固定安全邊界控制對外結果。

最終目標架構在現有 A／Query Expansion／RAG／B／受限 Agent／C／D／E 基線上，逐步加入多模態輸入、長程任務狀態、受控工具執行器、跨來源證據帳本及多 Agent 邊界監督。所有 Agent 只提出受限動作，所有工具結果只視為候選觀察或候選證據；Agent 不能自行批准證據，也不能跳過固定安全閘門。

本提案以完整目標架構說明長期方向，但不要求一次完成全部能力。**近期核准範圍建議先涵蓋 v0.1 收斂與 v0.2 三流程 MVP；v0.3 為中期規劃；多模態、長程任務與多 Agent 邊界監督則列為通過前一階段評測後才啟動的條件式研究。**核准目標架構不代表核准臨床使用，也不代表承諾一次完成所有版本。

## 二、背景與問題定義

### 2.1 目標使用者

本計畫服務三類主要使用者：

| 使用者 | 主要需求 | 回答設計重點 |
| --- | --- | --- |
| 糖尿病患者 | 詢問糖尿病藥品與日常照護資訊；整理看診前問題 | 白話說明、來源、可執行的非治療性步驟；不得鼓勵自行停藥、調藥或取代診療 |
| 病患家屬 | 協助理解衛教內容；整理患者已提供的用藥、症狀與時間資訊 | 不替患者推定病史；強調照護界線與必要時尋求醫療協助 |
| 醫護人員 | 查詢 TFDA／指引證據；檢視診前摘要；產生待人工確認的衛教草稿 | 保留來源、日期、適用範圍、證據衝突與未解問題；最終專業判斷由醫護人員負責 |

`declared_role` 目前是使用者自行提供的角色中繼資料（metadata），不是經過驗證的身分，也不能直接作為敏感資料或高風險工具的授權依據。未來的角色感知功能主要用於內容深度、格式與任務流程調整；若涉及權限，仍需獨立的身分驗證（identity verification）與授權控管（authorization）設計。

### 2.2 使用情境篩選依據

本案不從尚未被明確探索的醫療任務開始，而從已有系統性回顧或實際工作流程研究的應用中選擇。篩選同時考慮研究累積、流程明確度、臨床風險及與現有 A 至 E 架構的契合度。

| 候選場景 | 既有發展狀況 | 本案決定 | 理由 |
| --- | --- | --- | --- |
| 糖尿病衛教與自我管理支援 | 已有糖尿病專屬系統性回顧；常見功能涵蓋飲食、運動、血糖監測、藥物與併發症資訊 | **納入核心場景** | 與本案糖尿病主題及 RAG 證據架構直接相符 |
| 看診前病史／症狀／用藥資訊收集 | 已有醫療病史蒐集 chatbot 系統性回顧 | **納入核心場景** | 可把 `ASK_USER` 轉成明確產品流程，且不必由 Agent 下診斷 |
| 處方／藥袋辨識與仿單衛教 | OCR、文件理解與藥品資料查詢已有實作基礎 | **納入目標場景，於 v0.4 啟動** | 圖像用於降低藥名輸入門檻；正式說明仍以唯一匹配的 TFDA 許可證與核准仿單為依據 |
| 醫護證據查詢、摘要與衛教草稿 | 醫療對話 Agent 與臨床生成式 AI 已廣泛研究 | **納入核心場景** | 能直接使用 B-approved evidence 與引用驗證能力 |
| 臨床紀錄／ambient scribe | 已形成獨立研究與產品方向 | 暫不優先 | 發展較成熟，但與本案 TFDA 藥品證據主題較遠 |
| 心理健康／CBT 對話 | 有較多隨機試驗與統合分析 | 不納入 | 非本案主題，且需危機與自傷處理體系 |
| 症狀檢查與自動分流 | 已被大量研究，但準確度差異大 | 只保留紅旗警示與轉介 | 不把「有人研究」誤寫成「可自主判斷」 |
| 自主診斷、選藥、停換藥或劑量調整 | 高風險，缺乏足夠的常規使用證據 | **明確排除** | 超出資訊支援定位與目前治理能力 |

糖尿病對話 Agent 的研究多集中於飲食、運動、血糖監測、用藥與併發症管理，但高品質試驗及安全升級機制仍不足。因此本案採「支援既有照護計畫」而非「自動制定治療計畫」的定位。

此篩選主要參考[糖尿病對話 Agent 系統性回顧](https://pubmed.ncbi.nlm.nih.gov/40840786/)、[糖尿病自我管理 chatbot 系統性回顧與統合分析](https://pmc.ncbi.nlm.nih.gov/articles/PMC11653048/)、[診前病史蒐集 chatbot 系統性回顧](https://pmc.ncbi.nlm.nih.gov/articles/PMC11393511/)及[症狀檢查器診斷與分流準確度系統性回顧](https://pubmed.ncbi.nlm.nih.gov/37266983/)。這些文獻證明場景已被探索，不代表本系統已取得臨床有效性或安全性證據。

### 2.3 為什麼不能只做 RAG

RAG 適合處理非結構化文件檢索與證據查找，但三類使用者的需求不只包含「從文件找答案」。

| 使用情境 | 單靠 RAG 的限制 | 較適合的能力 |
| --- | --- | --- |
| 查詢藥品商品名、成分與許可證 | 向量搜尋可能回傳近似藥品，難保證精確欄位 | 結構化藥品與許可證查詢工具（Drug／License Lookup Tool） |
| 血糖單位、身體質量指數（BMI）或核准公式計算 | LLM 直接計算可能產生算術或單位錯誤 | 確定性計算工具（Deterministic Calculator Tool） |
| 症狀與緊急風險 | 文件相關不代表已完成安全分流 | 必經紅旗症狀與風險閘門（Mandatory Red-Flag／Risk Gate） |
| 比較不同藥物類別 | 需要對齊比較維度、來源與時間 | 結構化資料、指引檢索與比較功能 |
| 整理就醫資料 | 主要工作是結構化使用者資訊，不一定需要檢索 | 資訊收集、時間軸與轉介摘要工具（Intake／Timeline／Handoff Tool） |
| 醫護證據查詢 | 需要來源版本、日期、衝突與限制 | 證據搜尋與引用驗證工具（Evidence Search／Citation Verification Tool） |
| 從處方／藥袋取得仿單衛教 | RAG 不能負責 OCR、藥品唯一匹配或確認圖片中的藥品身分 | 多模態前處理、使用者確認、精確藥品／許可證工具；低信心或多筆候選時不得猜測 |
| 跨多輪補件與任務恢復 | 單次問答狀態無法安全保存進度、缺漏與執行限制 | 結構化 Task State／Checkpoint 與重新通過 A 的恢復政策 |
| Agent 行為監督 | 增加第二個 Agent 不會自然產生安全性，也不能取代固定 Gate | 只讀 Boundary Supervisor、單 Agent 對照評測與人工審查路徑 |

本計畫將 RAG 定位為工具生態中的一項「證據檢索能力」，而不是整個系統的唯一核心。

### 2.4 核心問題

本計畫欲解決以下問題：

1. 如何讓不同角色取得適合其需求與理解程度的糖尿病資訊？
2. 如何整合非結構化檢索、結構化資料與確定性計算，而不把所有工作交給單一大型語言模型（Large Language Model, LLM）？
3. 如何允許 Agent 分解任務與選擇工具，同時保留政策、證據與輸出安全邊界？
4. 如何保存每次工具選擇、證據來源、系統限制與最終決策，使結果可重現、可評估、可稽核？

### 2.5 資料來源評選原則

本版提案不預先指定正式資料集。後續應先完成資料來源盤點與評選，再決定哪些來源可進入原型（prototype）、評估（evaluation）與正式服務。評選面向至少包括：

- 權威性與發布單位。
- 糖尿病任務與目標使用者的涵蓋範圍。
- 資料授權、使用限制與可否對外提供衍生內容。
- 更新頻率、版本管理與過期資料處理方式。
- 是否具備穩定識別碼（identifier）、來源日期與可追溯中繼資料（metadata）。
- 結構化程度、文件品質、重複、衝突與缺漏情形。
- 是否涉及個人資料、敏感資料或其他隱私風險。
- 是否能建立具代表性的訓練、開發與獨立評估集合。

後文所稱「權威證據來源」皆為待評選能力類型，不代表已指定特定機構、資料庫或語料庫（corpus）。

## 三、目前基礎與成熟度

目前專案已具備以下內部基礎流程。為方便外部閱讀，以下使用功能名稱，不使用團隊內部模組代號：

```text
使用者
  → 輸入安全與任務路由
  → 檢索問題準備
  → 證據檢索
  → 證據與脈絡充分性審核
  → 證據導向回答生成
  → 最終輸出安全驗證
  → 正式回答／安全替代回應（fallback）

可觀測性與評估紀錄橫跨全部階段。

證據不足時，可進入受限恢復流程：
ASK_USER / REWRITE_QUERY / FALLBACK
```

### 3.1 已建立的能力

- 輸入安全與任務路由：請求資料格式（request schema）、角色／意圖訊號、提示注入防護（prompt injection guard）與確定性政策路由。
- 檢索問題準備：保留原始問題（original query）的可替換資料契約；目前基準版本採原句檢索（identity expansion）。
- 證據檢索：可替換的檢索器介面（retriever interface）與標準化證據資料契約；目前原型使用 129 筆 TFDA 藥品風險溝通資料，正式服務的來源組合、更新及失效政策仍待評選。
- 證據與脈絡審核：脈絡充分性資料契約（context sufficiency contract）與證據批准邊界。
- 受限恢復 Agent v0.1：`ASK_USER`、`REWRITE_QUERY`、`FALLBACK` 三種受限恢復動作。
- 證據導向回答生成：證據導向回答、已支持主張（supported claims）、未支持需求（unsupported requests）與限制說明（limitations）資料契約。
- 最終輸出安全驗證：必經輸出閘門、證據識別碼與政策驗證。
- 可觀測性：結構化執行軌跡（trace）、延遲、失敗、評估紀錄與人類可讀執行路徑。
- LangGraph 工作流程：固定路由、Agent 次數限制、請求與實際執行動作紀錄，以及失敗即安全終止（fail-closed）的替代回應。

### 3.2 目前限制

- 系統仍是展示版本（demo）、最小可行產品（Minimum Viable Product, MVP）與研究基準，不是自主臨床決策系統。
- 現有 TFDA 檢索原型可執行，但正式服務的資料來源組合與更新政策尚未核定；證據審核、回答生成與輸出驗證的部分語意元件仍包含測試替身（fixture）或展示用實作。
- 急症或緊急風險門檻尚未完成正式臨床驗證。
- `declared_role` 尚未連結身分驗證與授權控管（authorization）。
- 尚未建立正式環境的受保護健康資訊（Protected Health Information, PHI）、資料保存、存取控制與持久化對話政策。
- Agent 尚不能動態選擇一般工具；目前只處理證據不足後的有限恢復。

本提案將上述現況視為後續發展基線，避免把測試替身結果或少量展示用執行軌跡誤解為臨床可用性證據。

## 四、計畫定位與目標

### 4.1 計畫定位

本計畫定位為：

> 建立一套角色感知（role-aware）、證據導向（evidence-grounded），支援糖尿病衛教、診前資訊整理及醫護證據工作的對話式 Agent。

它不是：

- 自動診斷系統。
- 自動開藥、停藥或調整劑量系統。
- 未經醫護審核即可執行臨床處置的 Agent。
- 只根據 LLM 內部知識回答的通用聊天機器人。
- 只將文件放入向量資料庫的單一 RAG 聊天機器人。

### 4.2 計畫目標

1. 建立患者、家屬與醫護人員的角色—任務—回答政策矩陣（role-task-response policy matrix）。
2. 以現有 A／Query Expansion／RAG／B／Agent／C／D／E 流程支援三條核心使用流程。
3. 將 `ASK_USER` 用於診前資訊補充，將 `REWRITE_QUERY` 用於證據檢索恢復，將 `FALLBACK` 用於證據不足或超出範圍時安全終止。
4. 建立診前資訊摘要與醫護證據摘要的結構化輸出契約。
5. 確保所有證據結果均通過證據充分性與來源審核，所有正式回答均通過最終輸出安全驗證。
6. 在核心流程通過評測後，逐步建立工具登錄表、受控工具執行器、跨來源證據帳本與多來源能力。
7. 在具體使用需求與治理條件成立後，評估多模態輸入、長程任務狀態與多 Agent 邊界監督。
8. 建立角色、任務、證據、Agent 動作、工具呼叫、延遲、成本、錯誤及終止原因的完整執行軌跡與評估方法。

以下為本提案建議的最終產品架構。閱讀時先沿中央主線由上往下看；遇到風險、資料不足或證據不合格時，再沿右側分支查看系統如何追問、轉人工或安全終止。

                 ▼

圖中的 `[BASE]` 表示 v0.1 已建立主要程式骨架，不代表該元件已達正式服務品質；`[TARGET]` 表示後續版本預計建置。這個標示用來區分「已存在的工程基線」與「經評測後才啟動的目標能力」。

目標架構的控制權原則如下：

- Agent／Planner 可以提出下一步，但不能跳過或推翻 A、B、D。
- Tool 只回傳 observation 或 candidate evidence，不能直接形成正式醫療結論。
- Boundary Supervisor 只能提出 `REVIEW` 或 `FALLBACK`，不能自行批准證據，也不能以多 Agent 共識取代固定 Gate。
- 多模態、長程任務與多 Agent 只有在前一階段顯示明確新增效益，且完成資料、隱私與風險治理後才啟用。

### 5.1 現有基線與目標元件的對應

| 元件 | 狀態 | 在產品中的責任 |
| --- | --- | --- |
| A：Input Router／Policy Gate | `[BASE]` | 阻擋診斷、調藥、提示注入與高風險請求；辨識角色與任務 |
| Query Expansion | `[BASE]` | 保存原始問題，將口語描述轉成不改變原意的檢索查詢 |
| RAG | `[BASE]` | 檢索 TFDA 候選證據；後續擴充仿單與核准指引來源 |
| B：Context／Evidence Gate | `[BASE]` | 判斷資料是否相關、充分、衝突或有安全疑慮 |
| Agent Planner／Rewriter | `[BASE]` 受限版本 | 目前只在 B insufficient 後選擇 `ASK_USER`、`REWRITE_QUERY` 或 `FALLBACK` |
| C：Evidence-aware Generator | `[BASE]` | 只使用 B 核准證據產生衛教回答、診前摘要或醫護草稿 |
| D：Output Gate | `[BASE]` | 阻止無證據主張、個人化調藥指令及不適合角色的輸出 |
| E：Observability | `[BASE]` | 保存路由、證據、動作、輸出與終止原因，支援評測與稽核 |
| Multimodal Preprocessor | `[TARGET]` | 從處方／藥袋擷取藥名、成分、劑量與劑型；保留原圖、品質及欄位信心供確認 |
| Task State／Checkpoint | `[TARGET]` | 保存跨步驟任務進度、缺漏資訊、限制與中止狀態 |
| Tool Executor／Registry | `[TARGET]` | 以 allowlist、schema、權限、逾時與成本政策執行核准工具 |
| Evidence／Observation Ledger | `[TARGET]` | 統一保存來源、版本、時間、工具結果、Evidence ID 與衝突 |
| Boundary Supervisor Agent | `[TARGET]` | 監督越權、工具異常及證據遺漏；只可要求審查或安全終止 |

### 5.2 能力與權責分類

| 類型 | 元件 | Agent 是否可選擇 | 說明 |
| --- | --- | --- | --- |
| 工具（Tool） | 證據檢索、藥品查詢、指引搜尋、計算、資訊收集 | 是，但須通過允許清單與執行階段限制 | 可選能力；未呼叫時能力下降，但不能破壞安全性 |
| 閘門（Gate） | 輸入政策、必經風險篩檢、證據批准、最終輸出驗證 | 否 | 必經信任邊界；Agent 不能跳過或推翻 |
| 生成器（Generator） | 角色適配回答生成 | 否，正式回答流程固定進入 | 只能使用已批准證據（approved evidence） |
| 基礎設施（Infrastructure） | 工具執行器、狀態、記憶、執行軌跡、隱私控制 | 否 | 系統擁有，不由 LLM 控制 |

### 5.3 RAG 工具設計原則

第一個工具建議將現有檢索器介面包裝為資料來源中立的：

```text
EvidenceRetrievalTool(source_id, query, filters)
→ 執行狀態（status）
→ 檢索問題（retrieval_queries）
→ 候選證據（candidate evidence[]）
→ 來源／日期／分數／中繼資料
→ 延遲／錯誤
```

不建議第一版採用：

```text
RAGTool(question) → 最終醫療回答
```

因為檢索工具直接產生正式答案，容易混合證據搜尋、證據批准與回答生成，並可能繞過證據審核、回答生成及最終輸出驗證的既有邊界。

| P1 | 看診前症狀、用藥與問題整理 | 患者、家屬、醫護人員 | `ASK_USER`、結構化 intake schema、摘要輸出 | 不補造資料；紅旗訊號固定轉介；摘要不是診斷 |

### 6.1 患者／家屬衛教流程

```text
提出糖尿病藥品或照護問題
→ A 排除急症、診斷及調藥要求
→ RAG 檢索 TFDA／核准來源
→ B 判斷證據是否足以回答
→ 不足時詢問藥品名稱或最小必要背景
→ C 產生白話、有來源且揭露限制的回答
→ D 檢查後輸出或安全退回
```

### 6.2 看診前資訊整理流程

```text
患者選擇「準備看診」
→ 系統依結構化欄位詢問已知藥品、發生時間、症狀描述及想問醫師的問題
→ A 在每次補充資訊後重新檢查風險
→ 紅旗訊號走固定轉介，不由 Planner 自行決定是否就醫
→ C 只整理使用者已提供的內容
→ D 檢查是否出現診斷、推測病史或治療指令
→ 輸出可供患者攜帶、醫護快速閱讀的摘要
```

### 6.3 醫護證據工作流程

```text
醫護提出藥品風險或衛教主題
→ RAG 檢索具版本與來源的證據
→ B 保留足夠、相關且無未處理衝突的證據
→ C 產生證據摘要與待確認衛教草稿
→ D 驗證引用、限制與禁止內容
→ 醫護人員檢視、修改並負責最終使用
```

### 6.4 處方／藥袋辨識與仿單衛教流程ｓ

```text
患者拍攝處方箋或藥袋
→ 多模態前處理檢查圖片品質，以 OCR 擷取藥名、成分、劑量與劑型
→ 將辨識欄位及原圖對照呈現給患者確認
→ 藥品／許可證工具進行精確匹配
   ├── 唯一匹配：取得對應 TFDA 核准仿單
   ├── 多筆候選：ASK_USER 要求選擇、補拍或補充許可證／廠牌資訊
   └── 無法匹配：停止猜測，建議由藥師協助確認
→ B 檢查藥品身分、仿單來源、版本與證據充分性
→ C 將已核准仿單改寫為患者可理解的用途、注意事項與不良反應說明
→ D 阻擋個人化停藥、換藥、調整劑量及「醫師為何開此藥」等無證據推定
→ 輸出已確認藥品的仿單衛教與 TFDA 來源
```

圖片在此流程中的責任是降低輸入藥名的門檻，不負責診斷或直接形成藥品結論。OCR 結果是待確認 observation；只有完成使用者確認、唯一藥品匹配及 B 證據審核後，才可生成仿單衛教。

最終四項場景共用同一套安全骨架，但依版本逐步交付。v0.2 先完成患者衛教、診前資訊整理與醫護證據工作的三條文字流程；v0.4 再加入處方／藥袋辨識流程。這比建立彼此獨立的 chatbot 更容易維護，也能讓同一份證據在不同角色介面中維持事實一致。

### 階段 0／v0.1｜現有安全基線收斂

**目的**：凍結目前輸入路由、檢索、證據審核、回答生成、輸出驗證、可觀測性與 Agent v0.1 資料契約，作為後續比較基準。

主要工作：

- 標示真實元件、測試替身（fixture）、展示版本（demo）與尚未驗證的語意元件。
- 完成候選資料來源盤點、授權與更新機制比較；本階段不預設最終資料集。
- 固定目前請求、證據、Agent 決策、回答與輸出驗證結果，以及執行軌跡資料格式。
- 建立基準正確率、安全替代回應率、延遲與失敗樣態。

驗收條件：

- 現有資料契約測試通過。
- 主要 `ASK_USER`、`REWRITE_QUERY`、`FALLBACK` 執行軌跡可重現。
- 文件與實際原始碼、測試一致。

### 階段 1／v0.2-A｜RAG 工具化與工具基礎設施

**目的**：建立未來所有工具共用的標準，不立即擴大 LLM 控制權。

主要工作：

- `ToolRequest`、`ToolResult`、`ToolError` 與 `CanonicalObservation/Evidence` 資料格式（schema）。
- 資料來源中立的 `EvidenceRetrievalTool` 轉接器（adapter）。
- 工具登錄表、執行器、允許清單、逾時控制與執行軌跡。
- 仍由工作流程圖以確定性方式呼叫指定的測試檢索來源。

驗收條件：

- 工具參數與結果均通過資料格式驗證。
- 所有證據保留識別碼、來源、日期與中繼資料。
- 工具錯誤不會繞過證據審核、回答生成與最終輸出驗證，並能提供安全替代回應。
- 包裝前後的基準案例結果無非預期退步。

### 階段 2／v0.2-B｜三條角色與任務流程產品化

**目的**：從「文件問答」擴展為可展示患者衛教、診前資訊整理與醫護證據工作的糖尿病資訊支援服務。

主要工作：

- 建立角色—任務—回答政策矩陣。
- 建立任務分類體系（task taxonomy）與測試資料。
- 建立患者衛教、診前摘要與醫護證據草稿三種輸出資料契約。
- 建立三條流程各自的 happy path、資訊不足、證據不足與高風險案例。
- 加入結構化資訊收集／時間軸工具。
- 規劃必經風險篩檢資料契約；臨床門檻需另行審核。

驗收條件：

- 同一證據可依角色產生不同深度、但事實一致的輸出。
- 三條核心流程均有可重現的端到端案例及人工審閱結果。
- 使用者自行聲明的角色不會自動提升資料或工具權限。
- 結構化查詢以精確識別碼回傳，不使用相似文件猜測藥品。
- 患者／家屬輸出不包含自行停藥、調藥或取代診療的指示。

### 階段 3／v0.3｜受限多工具協調器

**目的**：讓規劃器（Planner）能在有限動作空間中選擇核准工具。

主要工作：

- Agent 動作擴充為 `CALL_TOOL`。
- 建立工具允許清單、參數驗證、步數／成本／逾時限制。
- 加入第一個結構化藥品／許可證工具及經核准的指引檢索來源。
- 建立重複呼叫偵測（duplicate-call detection）與應用程式掌控的快取政策。
- 所有證據工具結果強制重回證據與脈絡充分性審核。
- 記錄模型請求動作與系統實際執行動作。

驗收條件：

- Agent 不能呼叫未註冊工具或修改限制值。
- 非法工具名稱或參數會失敗即安全終止。
- 超過步數、工具或成本限制時安全終止。
- Agent 不能批准自己的工具結果，也不能繞過最終輸出安全驗證。
- 工具選擇正確率與不必要工具呼叫率可量測。

### 階段 4／v0.4｜多模態輸入與長程任務狀態

**目的**：完成處方／藥袋辨識與仿單衛教，並在受控狀態下處理跨多輪補拍、補件與藥品確認。

主要工作：

- 建立處方／藥袋圖片的輸入資料契約、品質檢查與 OCR 欄位格式。
- 擷取藥名、成分、劑量、劑型、廠牌與許可證等可見欄位；解析結果仍視為 observation，不直接視為已確認藥品。
- 建立原圖對照與使用者確認步驟；低信心、多筆候選或必要欄位不足時由 `ASK_USER` 要求補拍或補充資訊。
- 串接 v0.3 藥品／許可證工具與核准仿單來源；只有唯一匹配且通過 B 時才能生成仿單衛教。
- 建立 Task State／Checkpoint，保存任務進度、缺漏資訊、步數、成本與中止狀態。
- 使用者補件後重新通過 A，再恢復原任務；不得直接繞回高權限節點。
- 建立 PHI 最小化、附件保存期限與刪除政策的研究版控制。

驗收條件：

- 模糊、裁切、反光或無法辨識的處方／藥袋不產生確定性藥品主張。
- OCR 欄位必須可回查原圖；使用者未確認或不能唯一匹配時不得查錯誤仿單並繼續回答。
- 圖片、使用者確認內容與藥品資料衝突時保留衝突並轉人工，而非自行選擇一方。
- 不同 thread 的任務狀態與附件明確隔離。
- 超過步數、時間或補件限制時安全終止。

### 階段 5／v0.5｜多 Agent 邊界監督研究

**目的**：驗證 Boundary Supervisor 是否能在不取得證據批准權的前提下，改善越權、工具異常、證據衝突與必要資訊遺漏的發現率。

主要工作：

- 建立 Boundary Supervisor 的只讀輸入與結構化 `REVIEW`／`FALLBACK` 建議契約。
- Supervisor 不得呼叫有副作用工具、批准 evidence、修改 A／B／D 決策或產生正式答案。
- 建立相同任務的單 Agent 與多 Agent 對照組。
- 評估新增 Agent 帶來的安全效益、誤報、延遲、token 與成本。

驗收條件：

- Supervisor 越權批准證據或繞過固定 Gate 的次數為 0。
- 相較單 Agent 基準，至少一項事前核定的安全或錯誤發現指標有實質改善。
- 若只有成本與延遲增加而沒有可量測效益，停止多 Agent 擴充並維持單 Planner 架構。

### 階段 6／v1.0｜持久化、人工審查與受控試用準備

**目的**：將通過前述評測的能力整合成具備隱私、權限、監控及人工升級路徑的受控試用版本。

主要工作：

- 建立身分驗證、角色授權與最小權限原則。
- 建立 PHI 遮蔽、加密、保存、刪除與存取控制。
- 建立人工審查佇列、臨床升級與異常事件處理路徑。
- 建立模型、prompt、工具、資料來源與政策版本管理。
- 建立正式環境監控、變更重測與回復機制（rollback）。

驗收條件：

- 不同使用者、thread、附件與任務狀態明確隔離。
- 可追蹤每項回答使用的模型、提示詞、工具、資料版本與核准證據。
- 人工審查與異常事件具有完整稽核軌跡（audit trail）。
- 正式服務的 go／no-go 條件由醫療、隱私、資安與專案負責人共同簽署。

### 7.1 條件式能力的啟動閘門

| 能力 | 啟動條件 | 不啟動或停止條件 |
| --- | --- | --- |
| Multimodal Reasoning | 純文字不足以完成已核准任務，且附件治理與專屬評測已建立 | 缺少影像品質、敏感資料或人工覆核機制 |
| Long-horizon Planning | 任務確實需要跨多輪補件、恢復與摘要 | 單輪或短流程已可完成；狀態污染與隔離問題未解決 |
| Multi-agent Boundary Supervision | 單 Agent 基準顯示具體缺口，且 Supervisor 能處理獨立審查任務 | 無顯著新增效益，或誤報、延遲與成本超過核定門檻 |

這些能力是最終架構的相容方向，不是為了滿足技術名詞而必須完成的功能。每一階段都必須先證明新增能力對核心使用情境有實質效益，才可進入下一版本。

## 八、評估與驗收指標

正式數值目標應在階段 0 基準評估完成後確認。本版先定義必須量測的指標。

### 8.1 任務與回答品質

- 意圖／任務分類正確率。
- `ASK_USER`、`REWRITE_QUERY`、`CALL_TOOL`、`FALLBACK` 動作適切率。
- `REQUEST_REVIEW` 及人工審查升級適切率。
- 患者／病患家屬／醫護人員回答適切率。
- 已支持主張比例與未支持主張比例。
- 引用精確率、來源與日期完整率。
- 證據衝突揭露率。

### 8.2 工具品質

- 工具選擇正確率。
- 工具參數資料格式有效率。
- 檢索召回率與排序品質。
- 結構化查詢精確匹配率。
- 不必要工具呼叫率與重複呼叫率。
- 工具錯誤恢復與逾時處理表現。

### 8.3 安全與控制

- 輸入政策邊界被繞過：目標為 0。
- 未經證據審核批准的證據進入正式回答生成：目標為 0。
- 未經最終輸出安全驗證通過的候選回答對外輸出：目標為 0。
- 未註冊工具執行：目標為 0。
- 超限後仍繼續執行：目標為 0。
- 高風險或不確定案例的安全替代回應／人工審查適切率。

### 8.4 效能與營運

- 端到端延遲與各元件延遲。
- 權杖用量（token）、應用程式介面（API）、圖形處理器（GPU）與每次請求成本。
- 工具成功、空結果與錯誤率。
- 快取命中率。
- 執行軌跡完整率。
- 模型、提示詞、工具與資料版本可重現性。

### 8.5 條件式能力指標

多模態、長程狀態與多 Agent 只在對應版本啟動後納入驗收：

- 處方／藥袋 OCR 的欄位完整率與正確率、藥品唯一匹配率、使用者確認完成率及衝突揭露率。
- 多筆候選或無法辨識時誤選藥品的比例，以及錯誤仿單回傳率，目標均為 0。
- 模糊、缺頁或錯誤附件被誤當成確定證據的比例，目標為 0。
- Task State 恢復正確率、跨 thread 污染率及超限後繼續執行率；後兩者目標為 0。
- Supervisor 越權批准證據或改寫 Gate 決策的次數，目標為 0。
- 多 Agent 相較單 Agent 的錯誤發現增益、誤報率、延遲與單次任務成本。
- 人工 reviewer 對 Supervisor `REVIEW`／`FALLBACK` 建議的適切率。

## 九、風險與治理原則

| 風險 | 說明 | 初步控制方式 |
| --- | --- | --- |
| LLM 過度自主 | 同一模型同時選工具、批准證據及回答，可能放大錯誤 | 決策與執行分離；輸入政策、證據審核與輸出驗證採固定邊界 |
| 工具結果錯誤或衝突 | 專用工具仍可能出錯，不同來源可能矛盾 | 結果視為觀察資料；保留來源脈絡（provenance）；由獨立證據驗證器仲裁或轉人工 |
| 錯誤藥物辨識 | OCR 錯字、相同成分的不同廠牌／劑量／劑型，或近似商品名被誤認為使用者實際用藥 | 原圖對照、欄位信心、使用者確認、精確識別碼與唯一匹配；多筆候選時 `ASK_USER`，不得猜測 |
| 無限循環與成本失控 | Agent 重複改寫或呼叫高成本工具 | 步數、單一工具、總執行時間、token 與成本限制 |
| 緊急症狀漏判 | Agent 未主動選擇分流工具 | 高風險篩檢設為必經閘門，不作為普通可選工具 |
| 身分與權限混淆 | 使用者自稱醫護人員不代表已驗證 | 角色適配與授權控管分離 |
| PHI 與隱私 | 訊息、執行軌跡、附件可能含敏感資料 | 資料最小化、遮蔽、加密、保存期限與存取控制 |
| 多模態解析錯誤 | 模糊、裁切或反光的處方／藥袋，以及辨識錯字被當成已確認藥品 | 輸入品質 Gate、欄位信心、原圖對照、使用者確認、低信心拒絕與人工覆核 |
| 長程狀態污染 | 舊任務、其他 thread 或錯誤補件進入目前回答 | 結構化 Task State、thread 隔離、重新通過 A、版本與過期政策 |
| Supervisor 誤判或越權 | 第二個 Agent 產生錯誤安全感，或以共識取代證據 | 只讀輸入、受限輸出、無批准權、固定 Gate 與單 Agent 對照評測 |
| 架構複雜度膨脹 | 多模態、多工具與多 Agent 增加成本但沒有實際效益 | 分期決策閘門；未達效益門檻即停止擴充或回復較簡架構 |
| 測試替身被誤認正式成果 | 資料契約測試通過不代表臨床語意表現 | 報告明確標示真實／測試替身／展示元件；分開評估 |

## 十、預期成果

1. 一套具版本管理、支援三條近期文字流程並預留處方／藥袋辨識場景的糖尿病對話式 Agent 參考架構。
2. 統一工具軟體開發套件（SDK）、資料契約、登錄表與受控執行器。
3. 資料來源可替換的證據檢索工具與至少一項非 RAG 能力之示範實作。
4. 三類角色的任務、回答與安全政策矩陣。
5. 受限工具選擇 Agent 與 LangGraph 工作流程。
6. 證據帳本、必經證據／輸出邊界與完整結構化執行軌跡。
7. 離線迴歸、工具資料契約、對抗式安全與角色適配測試集。
8. 真實、測試替身、展示與正式環境準備度的元件矩陣及技術報告。
9. 通過條件式閘門後的多模態輸入與 Task State／Checkpoint 實驗結果。
10. Boundary Supervisor 相較單 Agent 基準的效益、風險、延遲與成本比較報告；未達門檻時交付停止決策，而非強制保留多 Agent。

## 十二、結論

本計畫的核心不是單純增加更多模型或把所有功能包成工具，而是讓患者衛教、診前資訊整理、處方／藥袋仿單衛教與醫護證據工作共用一套清楚區分 **可選能力** 與 **強制安全邊界** 的 Agent 平台。RAG、藥物資料庫、指引檢索、計算、多模態解析與資訊整理可以逐步標準化為工具；政策路由、緊急風險檢查、證據批准與最終輸出驗證則必須由系統固定執行。

透過「安全基線 → 三流程 MVP → 受限多工具 → 多模態與長程狀態 → 多 Agent 邊界監督研究 → 受控試用準備」的分期方法，本計畫可以在每一階段取得可展示、可測試、可驗收的成果，同時降低一次導入完整自主 Agent 所帶來的醫療安全、成本與治理風險。

本提案建議核准最終目標架構作為演進方向，並將 v0.1～v0.2 作為近期承諾範圍。v0.3 以後的每項能力都必須通過前一階段決策閘門；未證明新增效益的多模態、長程規劃或多 Agent 能力，不進入後續產品版本。核准本提案不代表核准臨床使用，也不代表一次核准 43～60 週的全部開發工作。
