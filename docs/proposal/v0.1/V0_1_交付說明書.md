## 2. 交付摘要

### 2.1 交付的是什麼

v0.1 是一套安全邊界優先的糖尿病藥品資訊 Agent／RAG 研究基線：

```text
User request
    │
    ▼
A：輸入 Router + Policy Gate
    │
    ▼
Query Expansion
    │
    ▼
RAG Retrieval
    │
    ▼
B：Context / Evidence Gate
    │
    ├── PASS ──────────────────────────► C
    │
    └── INSUFFICIENT ─► bounded Agent
                           ├── ASK_USER
                           ├── REWRITE_QUERY ─► RAG ─► B
                           └── FALLBACK

C：Evidence-aware Generator
    │
    ▼
D：Mandatory Output Gate
    │
    ▼
Answer or fixed safe fallback

E：跨 A／RAG／B／Agent／C／D 的 trace 與 evaluation
```

Agent 不是最高權限控制者。它不能跳過 A、核准 B 證據、直接修改限制或繞過 D。

### 2.2 交付形式

本版本沒有 Web server、REST API、登入系統、部署 image 或正式 UI。交付物是：

- 可 import 的 Python package；
- CLI demos；
- 129 筆 TFDA 風險溝通 processed corpus；
- fixture 與真實 corpus retrieval adapter；
- 自動測試；
- JSONL observability；
- 研究 scripts、reports、results 與 runs。

### 2.3 一句話成熟度判斷

**可交付作為可重現的研究／教學 v0.1，不可交付作為可直接提供病人使用的正式醫療服務。**

## 4. 程式與責任邊界

| 目錄 | 責任 | 不應承擔的責任 |
|---|---|---|
| `a_router/` | 輸入 schema、prompt guard、signal 與 policy route | 產生醫療答案 |
| `query_expansion/` | 保存 original query、產生 retrieval queries | 決定 evidence 是否足夠 |
| `rag/` | fixture 或真實 TFDA retrieval | 自動把 retrieved document 當 approved evidence |
| `b_context_gate/` | canonical evidence contract 與 B decision | 生成最終答案 |
| `agent/` | 在 B insufficient 時選擇受限 recovery action | 跳過 A/B/D 或任意使用工具 |
| `c_generator/` | 依 B-approved evidence 產生 structured candidate | 核准自己使用的證據 |
| `d_output_gate/` | 強制驗證 candidate 與固定 fallback | 取代臨床驗證 |
| `e_observability/` | 記錄 trace、metrics 與 evaluation | 改變任何 gate decision |
| `workflow/` | LangGraph orchestration 與 error boundary | 隱式啟用 live model |
| `tests/` | 離線 contract、boundary、agent 與 workflow regression | 證明臨床有效性 |

正式 workflow 入口：

```python
from tfda_context_gate.workflow.runner import run_workflow
```

預設 `run_workflow()` 使用 fixture retriever、deterministic B 與 deterministic C，因此可以離線驗證 contract，但不代表真實 TFDA 問答品質。

## 6. 交付狀態與驗收分級

為避免把不同成熟度混在一起，本文件使用三個驗收層級：

| 層級 | 定義 | 本次狀態 |
|---|---|---|
| L1：離線 contract | 不需下載模型或 API key；驗證 schema、gate、graph、fixture trajectory | 已重新驗證 |

### 6.2 Fixture 驗收的正確解讀

Fixture workflow 只驗證控制流程。例如 P1 問胰島素注射位置時，fixture retriever 仍會回傳固定的飲食證據，C 也會形成固定飲食答案。這不是 bug 被忽略，而是明確證明：

- fixture 不能拿來展示真實問答品質；
- fixture PASS 只能證明 A/B/C/D contract 與 evidence boundary 按設計連接；
- 對外展示內容品質時必須使用 real retrieval，且仍需清楚標示 B/C/D 是 demo components。

### 10.1 L1：必要的離線驗收

從 workspace root：


- `AG-REWRITE-001`：只做 meaning-preserving rewrite，再走 RAG → B → C → D。
- `AG-FALLBACK-001`：一次 rewrite 後仍無證據，第二步 bounded fallback，不無限迴圈。

```bash
python3 -m tfda_context_gate.workflow.demo \
  --retriever fixture \

  --log-path /tmp/tfda-v01-workflow.jsonl
```

## 11. 操作 Runbook

### 11.1 系統不是常駐服務

v0.1 沒有 start server／stop server。每個 CLI command 都是一次性 process：

1. 啟用 virtual environment。
2. 從正確 working directory 執行 command。
3. 檢查 stdout status、exit code 與 JSONL trace。
4. Process 結束即停止；沒有背景 worker 需要關閉。

### 11.2 建議的展示順序

1. 先跑 tests，證明 boundary regression 為綠色。
2. 跑 fixture Agent 三案例，解釋 ASK_USER／REWRITE／FALLBACK。
3. 若完整 embedding stack 已驗收，再跑 real RAG smoke。
4. 最後才跑 live Planner，並在畫面上標示 provider、model 與「研究 demo」。

### 11.3 Trace 輸出

Agent demo 可輸出完整 JSONL：

```bash
python3 -m tfda_context_gate.agent.demo \
  --planner fixture \
  --retriever fixture \
  --trace-output /tmp/tfda-agent-v01.jsonl
```

Workflow demo 的 `--log-path` 是必填。Production 化前要決定固定 log location、rotation、retention、access control、encryption 與 PHI policy；不要直接把 `/tmp` 範例當正式設定。

### 11.4 更新 TFDA 資料

`00_download_and_inspect.py` 會連網下載且覆寫對應 run directory 的 raw data。更新前：

1. 設定新的 `TFDA_RUN_DIR`，不要直接覆蓋已交付 baseline。
2. 從 `tfda_context_gate/` 執行 phase 0、1。
3. 檢查 record count、schema、空值、IDs 與新 hash。
4. 重建 processed documents。
5. 重跑 retrieval smoke 與所有 tests。
6. 人工審閱資料差異後，才提升為新版本。

範例：

```bash
cd tfda_context_gate
```

## 12. 安全、隱私與使用限制

### 12.1 必須維持的控制權

- A 是輸入政策 authority。
- 只有 `G_GENERAL_EDUCATION` 可以進入一般 RAG。
- `declared_role` 只是使用者自述，不能提升資料或工具權限。
- Retrieved evidence 必須經 B 明確核准後才能交給 C。
- C 的 claim 必須保留 evidence IDs。
- 每一個 C candidate 都必須經 D。
- Agent 只能在 application-owned limits 內選擇既定 action。
- E 只能觀察，不能改變 decision。

### 12.2 禁止的對外宣稱

不能宣稱 v0.1：

- 能診斷糖尿病或藥品不良反應；
- 能提供個人化停藥、換藥或劑量決策；
- 已由 TFDA、醫院或醫療專業組織核准；
- 已完成臨床安全性或法規驗證；
- fixture answer 是 TFDA 真實回答；
- `declared_role=HEALTHCARE_PROFESSIONAL` 代表已核實專業身份；
- 所有 TFDA 資料都是最新、有效且未被後續資訊取代。

### 12.3 資料與 log 注意事項

目前 trace 可能包含 original query，雖有 query hash 與 secret redaction，但沒有 production PHI governance。測試與展示時不要輸入真實姓名、病歷號、電話、地址、API key 或可識別病人資訊。

## 14. 故障排除

| 現象 | 最可能原因 | 處理方式 |
|---|---|---|
| `No module named tfda_context_gate` | 不在 workspace root 或 PYTHONPATH 不含 root | 回到 workspace root，用 `python -m tfda_context_gate.module_name` 執行 |
| real RAG tests skipped | 未安裝 embedding stack | 安裝 requirements，重新確認 import 與 tests |
| `real TFDA retrieval requires…` | 缺 `langchain-huggingface`／`sentence-transformers` | 安裝完整 requirements；不要改用 fixture 冒充 real |
| 找不到 corpus | 路徑不存在 | 檢查 `--documents-path`、`TFDA_DOCUMENTS_PATH` 與 repo data |
| `Missing OPENROUTER_API_KEY` | live OpenRouter 未設定 key | 在 process env 或 workspace root `.env` 設定 |
| OpenRouter Planner timeout | provider、網路或 timeout | 檢查 endpoint；調整 `AGENT_REQUEST_TIMEOUT`；保存失敗 trace |
| Ollama 連線失敗 | server 未啟動或 model 未下載 | 啟動 Ollama、`ollama pull qwen3:1.7b`、檢查 base URL |
| LLM Planner 結構輸出失敗 | LangChain/provider 版本或 model output | 確認 requirements、model、structured-output 支援；系統應 fail closed |
| Workflow 回傳 FALLBACK | A/B/D 或 dependency boundary 生效 | 先看 `fallback_reason`、reason codes 和 E trace，不要直接移除 gate |
| Fixture 答非所問 | fixture 是固定 contract evidence | 改用 real retriever 做內容展示，但仍標示 B/C demo |
| JSONL 含不該保存的內容 | demo sink 非 production PHI solution | 停止收集、限制檔案權限、依組織政策清除與通報 |
| urllib3 LibreSSL warning | 系統 Python SSL stack | 使用維護中的 Python/venv；驗收網路功能時不可忽略 TLS 相容性 |
| LangGraph pending deprecation warning | serializer 未來預設值改變 | 升版前明確測試／設定 serializer，不能只隱藏 warning |
