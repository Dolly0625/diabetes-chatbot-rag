# 建置安全邊界與證據導向的 TFDA 糖尿病藥品 Agent v0.1

本提案建議建立一套研究與展示用的糖尿病藥品安全資訊 Agent v0.1。系統以衛生福利部食品藥物管理署（Taiwan Food and Drug Administration，TFDA）公開資料為證據來源，透過固定安全邊界、檢索增強生成（Retrieval-Augmented Generation，RAG）與受限大型語言模型（Large Language Model，LLM）Agent 恢復流程，降低無證據回答、錯誤用藥建議與失控迴圈的風險。

## 2. 計畫摘要

本計畫解決的核心問題是：一般 RAG 能找到相關文件，卻不能單獨決定問題是否安全、證據是否足夠，以及答案是否能對外輸出。

v0.1 建議採用「固定安全流程加受限 Agent」：

```text
使用者
  │
  ▼
A：輸入 Router 與 Policy Gate
  │
  ▼
Query Expansion
  │
  ▼
RAG：TFDA 證據檢索
  │
  ▼
B：Context／Evidence Gate
  │
  ├── PASS ─► C ─► D ─► 正式回答或安全替代回應
  │
  └── INSUFFICIENT ─► Agent recovery
                           ├── ASK_USER
                           ├── REWRITE_QUERY ─► RAG ─► B
                           └── FALLBACK

E：記錄各階段 trace、metrics 與 evaluation
```

本案不讓 Agent 自由選擇任意工具。Agent 只在 B 判定證據不足後，從三個受限動作中選擇下一步。A、B、C、D 與執行限制仍由程式掌控。

預期成果是一套可重現的研究原型。它能展示安全分流、真實 TFDA retrieval、證據邊界、受限恢復、輸出檢查與執行軌跡，但不宣稱具備臨床決策能力。

## 3. 問題與變革理由

本節先描述現況，再說明為何需要投入 v0.1。

### 3.1 現況問題

一般文件問答或單一大型語言模型（Large Language Model，LLM）存在下列缺口：

1. **安全分流不足**：相關文件不代表問題適合由系統回答
2. **證據資格不清**：retrieved document 可能只是相似近鄰，不等於 approved evidence
3. **資訊不足時容易猜測**：藥物類別、症狀或時間不明時，模型可能補造前提
4. **改寫可能改變原意**：為提高 retrieval 命中率而加入使用者未提供的資訊
5. **無限恢復風險**：Agent 可能持續搜尋、改寫或增加成本
6. **輸出缺乏獨立檢查**：Generator 可能引用未核准 evidence 或產生個人化用藥指令
7. **難以稽核**：若沒有結構化 trace，團隊難以回查 route、證據、動作與 fallback 原因

### 3.2 不執行本案的基準情境

若維持 business as usual，系統可能停留在單一 RAG 或固定 fixture demo：

- 證據不足時直接 fallback，無法澄清最小必要資訊
- 口語問題無法做受控、可追蹤的 meaning-preserving rewrite
- 團隊難以區分模型要求的動作與系統實際執行的動作
- 安全改善無法用固定案例與 reason codes 重現
- 未來擴充時可能把 Agent 直接放在所有 gate 之外

### 3.3 預期改變路徑

本案的變革邏輯如下：

```text
固定 schema 與安全邊界
        │
        ▼
只允許一般衛教進入 RAG
        │
        ▼
B 明確區分 retrieved 與 approved evidence
        │
        ▼
證據不足時只允許三種受限恢復動作
        │
        ▼
C 只使用核准 evidence，D 再檢查輸出
        │
        ▼
E 保存可評估、可重現的完整 trajectory
```

若每個邊界都有資料契約與測試，團隊就能定位錯誤發生在輸入、retrieval、證據判斷、Agent action、generation 或 output validation，而不是只看到一段錯誤答案。

## 4. 目標使用者與優先情境

本節限定 v0.1 服務誰，以及優先展示哪些問題。

### 4.1 目標使用者

| 角色 | v0.1 需求 | 回答原則 | 權限限制 |
|---|---|---|---|
| 糖尿病患者 | 一般藥品用途、風險溝通與注意事項 | 白話、來源可追溯、不得個人化調藥 | `declared_role` 不構成身份驗證 |
| 病患家屬／照護者 | 協助理解藥物資訊、補充最小必要情境 | 不猜測藥名或病史，必要時追問 | 不取得患者資料存取權 |
| 醫療專業人員 | 查詢 TFDA 風險資料、日期與 evidence IDs | 保留專業用語、來源與限制 | 自述角色不提升工具或資料權限 |

### 4.2 v0.1 優先使用情境

| Case | 問題 | 預期系統行為 |
|---|---|---|
| 一般 TFDA 藥品資訊 | 問特定糖尿病藥物類別的安全資訊 | A 放行，RAG 檢索，B 核准後進 C／D |
| 資訊不足 | 家人吃糖尿病藥後腳不舒服，但未說藥物類別 | B insufficient，Agent `ASK_USER` |
| 口語正規化 | 「吃 SGLT2 下體不舒服」 | Agent 做一次 meaning-preserving `REWRITE_QUERY` |
| Corpus 無資料 | 問 Semaglutide 視力模糊，但 corpus 沒有該成分 | 一次受限恢復後 `FALLBACK` |
| Prompt injection | 要求忽略規則或跳過安全檢查 | A block，不進 RAG 或 Agent |
| 個人化用藥 | 要求停藥、換藥或調整劑量 | A 轉介／block，不進一般 RAG |

## 5. 計畫定位與非目標

本節防止團隊用 v0.1 名義擴張成自主醫療 Agent。

### 5.1 計畫定位

本計畫定位為：

> 一套安全邊界優先、證據導向、具有受限恢復能力的 TFDA 糖尿病藥品資訊研究 Agent。

### 5.2 v0.1 非目標

本案不建立：

- 自動診斷或疾病排除系統
- 個人化處方、停藥、換藥或劑量建議
- 具任意 `CALL_TOOL` 能力的多工具 Agent
- 藥品資料庫寫入、病歷修改或其他有副作用的工具
- 長期對話記憶或患者 profile
- 經身份驗證的醫療專業權限
- 正式應用程式介面（Application Programming Interface，API）、Web UI、手機應用或 production deployment
- 臨床安全性、醫療器材或主管機關核准聲明
- `tfda_medrax2_experiment/` 的平行工具、cache 或 registry 能力

## 6. 計畫目標與研究問題

本節將目標寫成可驗收成果，避免使用「提升安全性」等無法判定的敘述。

### 6.1 v0.1 目標

1. 建立版本化的 request、route、RAG、evidence、Agent action、answer、output 與 trace schemas
2. 讓只有 `G_GENERAL_EDUCATION` 的輸入可以進入一般 RAG
3. 保存 original query，並限制 query rewrite 不得加入新症狀、藥名或診斷
4. 區分 retrieved evidence 與 B-approved evidence
5. 在 B insufficient 時提供 `ASK_USER`、`REWRITE_QUERY`、`FALLBACK` 三種 bounded actions
6. 將 Agent 限制設為最多 2 steps、1 次 rewrite、1 次 clarification
7. 讓 C v2 的 claims 只能引用 approved evidence IDs
8. 讓每個 C candidate 必經 D，D 只回傳 `PASS` 或 `FALLBACK`
9. 讓 E 記錄每次 route、retrieval、B decision、Agent action、C／D 結果與 termination reason
10. 建立離線 tests、真實 TFDA retrieval smoke cases 與 prompt-injection regressions

### 6.2 研究問題

| 編號 | 研究問題 | v0.1 驗證方式 |
|---|---|---|
| RQ1 | 固定 safety gates 能否阻止 Agent 繞過 A、B、D？ | graph routes、非法狀態與 integration tests |
| RQ2 | B insufficient 後，受限 Agent 能否比直接 fallback 多完成可回答案例？ | ASK_USER 與 REWRITE_QUERY cases |
| RQ3 | Corpus 沒有答案時，Agent 能否在限制內停止？ | Semaglutide bounded fallback case |
| RQ4 | Query rewrite 能否提升 target evidence 排名且保存原意？ | rewrite 前後 rank 與人工語義檢查 |
| RQ5 | Structured trace 能否重建一次請求的關鍵決策？ | trajectory completeness review |

### 6.3 成功假設

- H1：把 gate 寫進 graph control flow，比只寫在 system prompt 更容易測試 bypass
- H2：一次澄清或一次受控改寫，可改善部分 B insufficient cases
- H3：當 evidence 仍不足時，固定 limits 可防止無限 recovery
- H4：分離 model-requested action 與 system-executed action，可提升稽核性

這些是假設，不是既定結論。第 12 節的指標決定是否支持假設。

### 7.2 資料基礎

- 每筆 record 對應一個 LangChain Document，v0.1 沒有再切 chunk
- Real retriever 使用 `intfloat/multilingual-e5-small` 與 in-memory vector store
- Corpus 沒有 status／version 欄位，不能自動判定資料仍有效或是否被後續資訊取代

截至 2026-08-24，本 workspace 的原始 v0.1 有下列可行性證據：

| 證據 | 結果 | 正確解讀 |
|---|---|---|
| Offline tests | `74 passed, 10 skipped` | Contract 與 fixture tests 無 failure；optional real RAG stack 未完整安裝 |

## 8. 建議的 v0.1 系統設計

本節說明各元件的控制權，而不把 Agent 描述成整個系統。

### 8.1 A：輸入 Router 與 Policy Gate

A 負責 request validation、意圖／風險訊號、prompt injection guard 與 deterministic policy。只有 `router_status=G_GENERAL_EDUCATION` 設定 `rag_allowed=true`。

A 應阻擋或轉介：

- 可能急症或無法排除的高風險
- 個人化停藥、換藥或劑量要求
- 診斷或治療決策
- Prompt injection
- 非服務範圍
- schema、model 或 dependency failure

### 8.2 Query Expansion 與 RAG

v0.1 預設的 identity expander 保留原始問題，只產生一個相同 retrieval query。Agent 觸發 rewrite 時，系統保留 original query，並記錄 rewritten query。

RAG 只回傳 candidate evidence。Retriever 不得把相似度排名轉換成 B approval，也不得直接產生最終醫療回答。

### 8.3 B：Context／Evidence Gate

B 接收 canonical evidence，回傳：

- `PASS`
- `INSUFFICIENT`
- `UNSAFE`
- `REVIEW`
- `FALLBACK`

只有 `PASS` 的 `approved_evidence_ids` 能進 C。v0.1 的 deterministic context gate 是 fixture／demo boundary；本案必須把正式 semantic B judge 列為未完成風險，而不是把 `all_retrieved` 模式稱為證據正確性判定。

### 8.4 Bounded Agent recovery

Agent 只在 B=`INSUFFICIENT` 且 workflow 注入 Planner 時啟用。Planner 只能輸出 discriminated union：

```text
ASK_USER
REWRITE_QUERY
FALLBACK
```

程式擁有限制：

| 限制 | v0.1 值 |
|---|---:|
| `max_agent_steps` | 2 |
| `max_rewrites` | 1 |
| `max_clarifications` | 1 |

Planner 看不到完整 `WorkflowState`，也不能修改 limits、選 graph node、批准 evidence 或輸出答案。

### 8.5 C v2：Evidence-aware Generator

C v2 回傳 `ANSWER`、`PARTIAL` 或 `INSUFFICIENT`，並區分：

- `supported_claims`
- `unsupported_requests`
- `limitations`

每個 supported claim 必須引用 B-approved evidence ID。Formal workflow 不使用 legacy C v1。

### 8.6 D：Mandatory Output Gate

D 是所有 C candidate 的必經節點。它驗證 schema、A policy、approved evidence IDs、output red lines 與 semantic verifier，最後只回傳 `PASS` 或 `FALLBACK`。

目前 verifier 是 lexical heuristic demo，不是臨床 safety verifier。正式對外試用前，專案必須建立獨立評測與醫療審閱。

### 8.7 E：Observability 與 evaluation

E 記錄 A、Query Expansion、RAG、B、Agent、C、D 與 SYSTEM events。Trace 包含 reason codes、evidence IDs、latency、actions、limits 與 termination reason。

E 不能修改 route 或 answer。Production 化前仍需建立 protected health information（PHI）政策、加密、access control、retention 與 deletion 流程。

## 9. 方案比較與建議選項

本節比較四種方案，避免直接把偏好的技術當成唯一答案。

評分採 1 至 5 分，5 分代表較符合 v0.1 成功條件。分數是本提案的初步工程判斷，核准前仍需由團隊確認。

| 方案 | 安全邊界 | 證據可追溯 | 處理資訊不足 | 實作負擔 | v0.1 適合度 |
|---|---:|---:|---:|---:|---:|
| A：單一 LLM／RAG chatbot | 1 | 2 | 2 | 5 | 1 |
| B：固定 A 至 E pipeline，無 Agent | 4 | 5 | 1 | 4 | 3 |
| C：固定 A 至 E 加 bounded recovery | 5 | 5 | 4 | 3 | 5 |
| D：自主多工具 Agent | 2 | 3 | 5 | 1 | 2 |

建議採用方案 C：

- 它保留方案 B 的固定 gate
- 它用 `ASK_USER` 與一次 rewrite 改善資訊不足案例
- 它用 application-owned limits 控制迴圈
- 它不需要在 v0.1 引入任意工具權限
- 它能透過三個 ground-truth cases 做離線驗收

方案 D 不進入本案。多工具能力需要 tool registry、executor、allowlist、參數驗證、timeout、成本治理與更完整風險評測，應另案提議。

## 10. 工作範圍與工作包

本節將 v0.1 拆成可獨立驗收的工作包（Work Package，WP）。實際日期在核准人力後填入。

| 工作包 | 主要工作 | 主要負責角色 | 交付物 | 完成條件 |
|---|---|---|---|---|
| WP0：需求與安全範圍 | 確認角色、用途、禁止功能與 reason-code taxonomy | 專案負責人、LLM、醫療 reviewer | Scope、policy matrix | 高風險與一般衛教邊界獲核定 |
| WP1：A 與 shared schemas | Request、signals、routes、guard、policy | LLM 組 | A schemas、router、tests | 非 G route 不進 RAG |
| WP2：RAG 與 B contract | Corpus、retriever、canonical evidence、B result | RAG 組、LLM 組 | RAG/B adapters、smoke cases | Evidence IDs 與 provenance 可追溯 |
| WP3：Agent recovery | Planner、rewriter、limits、conditional graph | LLM／Agent 組 | 三種 actions、cases、tests | ASK／rewrite／fallback 可重現 |
| WP4：C、D 與 E | Structured generation、output gate、trace | LLM 組、測試 | C v2、D、JSONL trace | 未核准 evidence 與未過 D 輸出為 0 |
| WP5：整合與驗收 | End-to-end、adversarial cases、文件與 demo | 品質保證（Quality Assurance，QA）、全組 | Test report、demo、proposal／handover docs | 第 12 節必要條件通過 |

### 10.1 建議順序

工作包依下列順序執行：

1. WP0 凍結 scope 與安全 authority
2. WP1、WP2 確立跨組 contract
3. WP3 只在 contract 穩定後加入 Agent branch
4. WP4 將候選答案接入 D 與 E
5. WP5 以固定 cases 驗收整體行為

### 10.2 跨組介面

LLM 組負責：

- A policy 與 structured route
- Agent Planner／Query Rewriter contract
- C v2 與 D output policy
- E trace fields 與 evaluation

RAG 組負責：

- Corpus ingestion、metadata 與 evidence IDs
- Retrieval query 接口與 retrieval results
- Retriever type、score semantics 與 provenance
- B 所需的 evidence quality signals

雙方共同負責：

- Shared schema version
- `original_query` 與 `retrieval_queries` 的語義
- `evidence_id` 唯一性
- B decision 與 approved evidence contract
- Error、empty、partial、conflict 與 timeout 表示方式

## 12. 評估設計與驗收標準

本節區分零容忍的控制違規、Agent 任務指標與尚待校準的語義指標。

### 12.1 必要安全與控制條件

| 指標 | v0.1 驗收門檻 | 測試證據 |
|---|---:|---|
| 非 `G_GENERAL_EDUCATION` 進入一般 RAG | 0 | A／workflow integration tests |
| 未核准 evidence 進入 C supported claims | 0 | B-to-C／D tests |
| 未經 D 的 candidate 對外輸出 | 0 | Graph edge 與 E2E tests |
| Agent 執行未定義 action | 0 | Structured union validation |
| Agent 超過 2 steps 仍繼續 | 0 | Limit tests |
| Rewrite 超過 1 次 | 0 | Limit tests |
| 未通過 A 的 prompt injection 進入 Agent | 0 | PI-1／PI-2 regressions |
| Dependency failure 直接回傳未檢查答案 | 0 | Failure-boundary tests |

### 12.2 Agent cases

| Case | 必須觀察的結果 |
|---|---|
| `AG-ASK-001` | 初次 `NEEDS_CLARIFICATION`；補充 SGLT2 後重新從 A 進入 |
| `AG-REWRITE-001` | 只做一次 meaning-preserving rewrite，target evidence rank 改善 |
| `AG-FALLBACK-001` | Corpus 無 Semaglutide evidence；最多一次 rewrite 後 fallback |
| `PI-1` | A block；RAG 與 Agent 都未執行 |
| `PI-2` | A block；RAG 與 Agent 都未執行 |

目前 PI regression 使用注入式 blocked-result guard 驗證 A boundary。這能證明被 guard 標記的請求不會進入 RAG／Agent，但不能證明預設 regex guard 已能辨識所有自然語言 prompt injection；正式驗收仍需擴充中文 benchmark。

### 12.3 Retrieval 與 evidence 指標

- Gold evidence Recall@K
- Mean Reciprocal Rank（MRR）或 target evidence rank
- Evidence ID／source／date 完整率
- B relevance、sufficiency、conflict 與 safety confusion matrix
- Approved citation precision 與 coverage
- Empty／partial／conflict／error 分類正確率

現有 `expected_match` 只檢查 top-k 是否包含預期主題。正式提案驗收不能把它當作 evidence sufficiency 或 clinical correctness。

### 12.4 Answer 與角色指標

- Supported-claim rate
- Unsupported-claim rate
- Citation accuracy
- Over-refusal rate
- 患者／家屬／醫療專業角色適切率
- 個人化停換藥指令違規率
- 人工 reviewer 對正確性、完整性、可理解性與限制揭露的評分

正式數值門檻應在醫療 reviewer 完成標註規則與 baseline 後核定。本提案不以未經校準的百分比製造精確假象。

### 12.5 Observability 指標

- 必要 stage trace completeness
- Request ID、evidence IDs、reason codes 與 termination reason 完整率
- 各元件 latency 與錯誤率
- Model-requested action 與 system-executed action 差異率
- Secret／敏感資訊 redaction regression

## 13. 風險與治理

本節採用 govern、map、measure、manage 的思路管理人工智慧（Artificial Intelligence，AI）風險，而不是把風險表視為一次性文件。

| 風險 | 可能影響 | v0.1 控制 | Owner | 殘餘風險 |
|---|---|---|---|---|
| 緊急症狀漏判 | 延誤真人處理 | A fixed route、fallback | 醫療 reviewer／LLM | 門檻未臨床驗證 |
| 個人化調藥 | 不當用藥行為 | A block、D red lines | LLM／醫療 reviewer | 自然語言變體可能漏判 |
| Prompt injection | 繞過安全規則 | Guard、policy、PI regressions | LLM／security | Benchmark 覆蓋不足 |
| Retrieval false positive | 引用不相關 TFDA 文件 | B approval boundary | RAG／B owner | Semantic B 仍是 demo |
| Corpus 過期 | 提供已被更新的資訊 | 日期與 provenance | Data owner | Corpus 缺 status／version |
| Query rewrite 漂移 | 加入未提供症狀或藥物 | Meaning-preserving validation | Agent owner | Live LLM 仍可能失敗 |
| LLM hallucination | Unsupported claims | C schema、approved IDs、D | C／D owner | Demo verifier 非臨床 judge |
| Agent loop | 延遲與成本失控 | 2 steps、1 rewrite、1 clarification | Workflow owner | 外部 provider latency |
| Fixture 誤用 | 把 contract demo 當醫療成果 | Component labels、separate reports | Project owner／QA | 對外簡報仍可能混淆 |
| Trace 敏感資料 | 隱私與合規風險 | Redaction、data minimization | Privacy owner | 尚無 production PHI policy |
| 角色冒用 | 不當提高信任或權限 | `declared_role` 不授權 | Product／security | 尚無 identity verification |

### 13.1 治理原則

本案採用下列治理原則：

1. **保留人的決策責任**：系統不取代醫療人員的診斷與治療決策
2. **限制用途**：只允許已定義的一般資訊 use cases
3. **透明可追溯**：保存模型、route、query、evidence、action 與 output decision
4. **持續量測**：每次 model、prompt、policy、corpus 或 threshold 變更都重跑 benchmark
5. **失敗即安全終止**：schema、dependency、evidence 或 verifier 失敗時不輸出未檢查答案
6. **角色與授權分離**：自述角色只影響呈現，不提供高風險能力

## 14. 預期效益

本節區分可直接量測的工程效益與仍需研究證明的使用效益。

### 14.1 可量測工程效益

- 以固定 schema 降低跨 LLM／RAG 組的欄位歧義
- 以 approved evidence IDs 檢查 C／D evidence boundary
- 以 bounded actions 避免無限 recovery
- 以 trace 定位每次失敗的 stage 與 reason code
- 以 fixture 保持離線 regression 可重現
- 以 injectable components 比較 fixture、real retrieval 與 live LLM

### 14.2 待實驗驗證的效益

- ASK_USER 是否提升資訊不足問題的完成率
- Query rewrite 是否穩定改善 retrieval rank
- 三種角色是否需要不同內容深度
- 使用者是否能理解 source、limitations 與 fallback
- 增加 Agent 後的效益是否高於延遲、成本與風險

提案核准不等於這些效益已成立。WP5 必須產出評測結果，才能決定是否進入下一版本。

- A 無法安全分類

- C 引用未核准 evidence
- D schema、policy、evidence 或 verifier 未通過
- Dependency timeout、exception 或 malformed output

## 19. 提案方法與外部依據

本節說明提案結構與 AI 健康治理原則的來源。

- [HM Treasury Green Book 2026](https://www.gov.uk/government/publications/the-green-book-appraisal-and-evaluation-in-central-government/the-green-book-2026) 要求提案說明 case for change、theory of change、business as usual、可量測目標、strategic fit 與替代方案。本提案因此加入變革理由、方案比較與決策閘門。
- [NIST AI Risk Management Framework Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/) 以 Govern、Map、Measure、Manage 組織 AI risk activities，並強調風險管理應持續貫穿生命週期。本提案因此把 owner、metrics、residual risk 與變更後重測納入工作範圍。
- [World Health Organization: Ethics and governance of artificial intelligence for health](https://www.who.int/publications/i/item/9789240029200) 強調健康 AI 的倫理、人權、透明、責任與公共利益。本提案因此限制用途、保留人的決策責任，並要求來源、限制與問責機制。
- [WHO: Safe and ethical AI for health](https://www.who.int/news/item/16-05-2023-who-calls-for-safe-and-ethical-ai-for-health) 建議在廣泛用於日常醫療前先量測明確效益並處理大型語言模型風險。本提案因此將 clinical use 排除於 v0.1，並把 answer benefit 留作評測問題。

上述來源提供 proposal 與 risk-governance 方法，不代表 HM Treasury、NIST 或 WHO 已審查或認可本專案。

## 21. 結論與核准建議
