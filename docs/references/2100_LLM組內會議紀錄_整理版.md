# LLM 組內會議紀錄

- 會議時間：2026-08-20 21:00
- 主題：糖尿病照護 Chatbot 整體流程、LLM 安全守門與 RAG 串接規劃
- 文件目的：彙整目前共識、暫定技術設計與跨組待對齊事項，供團隊後續實作與討論參考。

## 一、會議摘要

本系統定位為本地部署的糖尿病照護 Chatbot，主要提供一般衛教與互動式照護資訊。設計原則為「安全判定優先於回答生成」：只有符合政策範圍的一般衛教問題，才會進入 RAG 檢索與答案生成流程；急症、個人化用藥、診斷／治療決策或系統異常，均應優先轉入攔截、轉介、追問或安全降級流程。

目前架構以 LLM 組負責 A 至 D 的守門、判定與生成流程；RAG 組負責知識檢索、重排序與來源文件管理。兩組之間須以固定標籤字典、版本化 JSON Schema 與可追溯的檢索結果進行串接。

## 二、整體 Chatbot 流程

    [使用者輸入]
            ↓
    A. Input Router + Policy Gate
       ├─ 非安全／非服務範圍：攔截、轉介或一次性澄清提問
       └─ 一般衛教（G_GENERAL_EDUCATION）
            ↓
       查詢擴充：保留原始問句，產生可檢索的查詢詞／子查詢
            ↓
    [RAG 檢索、重排序與來源回傳]
            ↓
    B. Contract Gate + Context Gate
       ├─ 格式、內容安全或相關性不符：回傳檢索回饋，重新檢索／安全降級
       └─ 通過
            ↓
    C. Generator
       ├─ 問題拆解與逐項作答
       └─ 依檢索內容整合為可讀回答
            ↓
    D. Output Gate
       ├─ 答案不安全、不相關或缺乏依據：拒答／資料不足／安全模板
       └─ 通過：回覆使用者

## 三、目前共識與設計原則

1. 採用多階段模組化管線（Prompt Chaining / Multi-stage Pipeline），將特徵抽取、安全裁決、檢索品質判定、答案生成與輸出驗證分離。
2. 輸入安全檢查採雙層 LLM：第一層抽取語意特徵，第二層輸出最終路由決策與可審計原因碼。
3. 第一層標籤與第二層路由碼皆須由固定字典約束，避免自由生成的近義標籤造成下游規則或檢索條件不一致。
4. 風險採最高風險優先原則；出現多個旗標時不得互相抵銷。
5. RAG 回傳內容在使用前仍須經過格式、安全與上下文相關性檢查，不可直接送入生成器。
6. 生成與輸出階段需保留「資料不足、無法回答」的安全出口，避免在證據不足時補全或臆測。
7. 內部可採問題拆解與多步驟推理提升穩定性；對使用者僅輸出經審核的結論、依據與必要說明，不輸出詳細內部推理歷程。

## 四、模組規劃與暫定技術設計

| 區段 | 主要責任 | 暫定作法／技術元件 | 主要輸出 |
| --- | --- | --- | --- |
| A. Input Router + Policy Gate | 辨識意圖、風險與可服務範圍 | 兩階段 LLM、固定 Label Dictionary、JSON Schema 驗證 | 結構化標籤、router_status、reason_codes |
| 查詢擴充 | 將可放行問題轉為較穩定的檢索請求 | LLM Query Rewriting／Query Expansion；保留原始問句 | 原始問句、查詢詞、子查詢或檢索條件 |
| RAG | 找回可信且相關的知識內容 | 索引與檢索、RRF 重排序、文件 Metadata 管理 | 排序後 chunks、分數、來源與日期等 Metadata |
| B. Contract Gate + Context Gate | 決定 RAG 回傳內容是否可供生成器使用 | 格式正規化、JSON Schema、Llama Guard 4（候選安全分類器）、LLM Judge | 通過／拒絕、上下文品質結果、回饋原因 |
| C. Generator | 依問題與通過的內容產生回答 | 本地 LLM、問題拆解、逐項回答與整合 | 具來源依據的草稿回答 |
| D. Output Gate | 驗證最終回答是否可對外送出 | LLM Judge、安全檢查、拒答／轉介模板 | 最終回答或安全降級回覆 |
| 共通層 | 可觀測性、除錯與稽核 | 結構化日誌、版本號、請求 ID、評測資料集與儀表板 | 可追溯的流程與品質紀錄 |

> 註：Llama Guard 4 為目前規劃採用的候選安全分類模型，仍需在本地部署條件、中文表現、延遲與分類準確度驗證後定案。

## 五、各階段功能定義

### A. Input Router + Policy Gate

第一層 LLM 僅負責抽取客觀語意特徵，不直接做政策裁決：

| 欄位 | 用途 | 暫定內容 |
| --- | --- | --- |
| intent_tags | 辨識提問目的 | 一般衛教、症狀資訊、診斷要求、一般藥品資訊、停換藥／劑量要求、非醫療 |
| risk_flags | 標記安全風險 | 可能急症、心理危機、個人化用藥、無法排除高風險、疑似注入 |
| context_modifiers | 補足語境，降低關鍵字誤判 | 時間、對象、極性、語言別 |

第二層 LLM 依上述特徵輸出最終路由碼與原因碼。原因碼應採固定代碼表，供除錯、監控與審計使用。

| 路由碼 | 處理方式 | 是否進入 RAG |
| --- | --- | --- |
| E_EMERGENCY | 顯示核准的地區化緊急處置引導 | 否 |
| U_URGENT_HUMAN | 提供真人評估、就醫或諮詢管道 | 否 |
| M_MEDICATION_REFERRAL | 轉介處方醫師或藥師；一般藥物資訊走限縮流程 | 原則上否 |
| R_POLICY_BOUNDARY | 說明能力邊界並提供合規就醫建議 | 否 |
| Q_CLARIFICATION | 僅針對安全分類所需的最小資訊進行一次性追問 | 否 |
| G_GENERAL_EDUCATION | 放行至檢索與生成流程 | 是 |
| O_OUT_OF_SCOPE | 說明服務範圍 | 否 |
| F_ROUTER_DEPENDENCY | 逾時、Schema 無效或系統異常時安全降級 | 否 |

### 查詢擴充

通過 A 階段後，將單一問句(User Input)拆解為可檢索的詞彙、同義表述或子查詢，並保留原始問句作為主要語意依據。查詢擴充僅協助檢索，不得改寫使用者意圖或自行加入未提供的醫療條件。

### B. Contract Gate + Context Gate

RAG 回傳結果需依序檢查：

1. 正規化格式與必要欄位是否完整。
2. 檢索內容本身是否含不安全或不應使用的資訊。
3. 使用者問題與檢索內容的相關性／上下文精確度（Context Relevance / Context Precision）。
4. 未達門檻時，回傳可行的檢索回饋，由 RAG 端調整查詢、過濾或重排序；不得將未驗證內容直接交由生成器。

### C. Generator

生成器在通過 B 階段後執行：

1. 再次進行生成前安全檢查。
2. 將複合問題拆為可回答的子問題。
3. 以通過驗證的檢索內容逐項回答子問題。
4. 將子問題整合為一致、易讀且符合衛教範圍的回覆；證據不足的部分應明確保留不確定性或拒答。

### D. Output Gate

最終回答送出前以 LLM Judge 檢查下列面向：

| 檢查項目 | 判定重點 |
| --- | --- |
| Answer Relevance | 回答是否直接回應使用者問題 |
| Faithfulness / Groundedness | 每項事實性主張是否可由檢索內容支持，且無矛盾或幻覺 |
| Abstention Accuracy | 證據不足或問題不可解時，是否正確說明無法回答，而非臆測 |
| Verbalized Confidence | 用語的確定程度是否與證據強度相符 |

未通過時，依失敗類型回覆資料不足、能力邊界、轉介建議或其他核准的安全模板。

## 六、LLM 與 RAG 串接資料契約（討論草案）

### LLM → RAG：建議最小請求內容

| 欄位 | 說明 | 舉例 |
| --- | --- | --- |
| request_id、schema_version | 供追蹤、除錯與契約版本管理 | request_id：req_20260820_0001<br>schema_version：v0.1 |
| user_raw_input | 完整保留原始輸入，避免擴充查詢取代原意 | 我最近剛驗出飯後血糖 180，想請問第二型糖尿病一般飲食該怎麼控制？ |
| retrieval_queries | 查詢擴充後的檢索詞或子查詢 | [第二型糖尿病 飲食控制, 飯後血糖 180, 糖尿病飲食衛教] |
| guardrail_result | intent_tags、risk_flags、context_modifiers、router_status、reason_codes | intent_tags：[一般衛教, 症狀資訊]<br>risk_flags：[]<br>context_modifiers：{ time_frame: 現在, target_subject: 本人, polarity: 肯定, language: zh-TW }<br>router_status：G_GENERAL_EDUCATION<br>reason_codes：[INQUIRY_DIETARY_EDUCATION, NO_CRITICAL_SYMPTOMS_DETECTED, MEETS_SAFE_SCOPE] |
| language、timestamp | 語言處理與稽核所需的基本資訊 | language：zh-TW<br>timestamp：2026-08-20T21:00:00+08:00 |

### guardrail_result：固定字典與 Payload 範例（討論草案）

guardrail_result 是 LLM 交給 RAG 的結構化安全與語意資訊。各欄位應由共同維護的 Label Dictionary 約束：中文名稱供文件閱讀，實際 Payload 建議使用固定的機器可讀 code。模型只能從允許的枚舉值中選取，不得自行生成近義詞、縮寫或新標籤；出現不在字典內的值時，應視為 Schema 驗證失敗並進入安全降級流程。

#### Payload 範例

~~~json
{
  "intent_tags": [
    "GENERAL_EDUCATION",
    "SYMPTOM_INFORMATION"
  ],
  "risk_flags": [],
  "context_modifiers": {
    "time_frame": "CURRENT",
    "target_subject": "SELF",
    "polarity": "AFFIRMATIVE",
    "language": "zh-TW"
  },
  "router_status": "G_GENERAL_EDUCATION",
  "reason_codes": [
    "INQUIRY_DIETARY_EDUCATION",
    "NO_CRITICAL_SYMPTOMS_DETECTED",
    "MEETS_SAFE_SCOPE"
  ]
}
~~~

上述範例對應的情境為：「最近飯後血糖 180，詢問第二型糖尿病的一般飲食控制方式」。其含義為一般衛教問題、未偵測到風險旗標，且可在既定政策範圍內進入 RAG。

#### 1. intent_tags：可複選的提問意圖

| 固定 code | 中文意義 | 使用時機舉例 |
| --- | --- | --- |
| GENERAL_EDUCATION | 一般衛教 | 詢問糖尿病飲食、運動、血糖監測的一般原則 |
| SYMPTOM_INFORMATION | 症狀資訊 | 詢問低血糖或高血糖可能出現的常見症狀 |
| DIAGNOSIS_REQUEST | 診斷要求 | 要求判定「這是不是糖尿病」或排除特定疾病 |
| GENERAL_MEDICATION_INFORMATION | 一般藥品資訊 | 詢問某類降血糖藥的通用用途或常見副作用 |
| MEDICATION_CHANGE_REQUEST | 停換藥／劑量要求 | 要求加減劑量、停藥、換藥或判定個人交互作用 |
| NON_MEDICAL | 非醫療 | 閒聊、與糖尿病照護無關的問題 |

#### 2. risk_flags：可複選的安全風險

| 固定 code | 中文意義 | 使用時機舉例 |
| --- | --- | --- |
| POSSIBLE_EMERGENCY | 可能急症 | 意識改變、昏迷、嚴重呼吸困難等立即危險描述 |
| MENTAL_HEALTH_CRISIS | 心理危機 | 自傷、他傷或迫切心理危機訊號 |
| PERSONALIZED_MEDICATION | 個人化用藥 | 依個人數值、病史或目前處方要求調藥 |
| HIGH_RISK_NOT_EXCLUDED | 無法排除高風險 | 資訊不足，但無法安全排除立即或嚴重風險 |
| PROMPT_INJECTION_SUSPECTED | 疑似注入 | 要求忽略規則、揭露系統提示或操控模型行為 |

#### 3. context_modifiers：固定語境值

| 子欄位 | 固定值範例 | 中文意義／用途 |
| --- | --- | --- |
| time_frame | CURRENT、PAST、HYPOTHETICAL | 現在、過去、假設情境 |
| target_subject | SELF、FAMILY_OR_CAREGIVER、THIRD_PARTY | 本人、家屬／照護者、第三人 |
| polarity | AFFIRMATIVE、NEGATIVE | 肯定、否定；用於避免將「沒有胸痛」誤判為有症狀 |
| language | zh-TW、zh-CN、en-US | 使用 BCP 47 語言代碼，供檢索與回覆語言處理 |

#### 4. router_status：只能擇一的最終路由

| 固定 code | 路由結果 |
| --- | --- |
| E_EMERGENCY | 緊急處置引導，不進 RAG |
| U_URGENT_HUMAN | 儘速真人評估／就醫轉介，不進 RAG |
| M_MEDICATION_REFERRAL | 個人化用藥轉介，原則上不進 RAG |
| R_POLICY_BOUNDARY | 超出診斷、治療決策等政策邊界，不進 RAG |
| Q_CLARIFICATION | 需最小必要資訊才能安全分類，進行一次性追問 |
| G_GENERAL_EDUCATION | 一般衛教，放行進入 RAG |
| O_OUT_OF_SCOPE | 非服務範圍，不進 RAG |
| F_ROUTER_DEPENDENCY | 逾時、Schema 無效或相依服務異常，安全降級 |

#### 5. reason_codes：可複選的可審計判定依據

reason_codes 用於記錄路由依據、監控與除錯；以下為目前可供討論的例子，完整清單與命名規則需在共同字典中定版。

| 固定 code 範例 | 意義 | 對應情境 |
| --- | --- | --- |
| INQUIRY_DIETARY_EDUCATION | 飲食衛教查詢 | 使用者詢問一般飲食控制原則 |
| NO_CRITICAL_SYMPTOMS_DETECTED | 未偵測到關鍵急症症狀 | 輸入未出現明顯立即危險線索 |
| MEETS_SAFE_SCOPE | 符合安全服務範圍 | 可提供一般衛教並放行至 RAG |
| REASON_ACUTE_HYPOGLYCEMIA | 急性低血糖疑慮 | 出現冒冷汗、意識不清等高風險組合 |
| REASON_PERSONALIZED_MEDICATION_REQUEST | 個人化用藥要求 | 依個人血糖或處方要求調整劑量 |
| REASON_PROMPT_INJECTION_SUSPECTED | 疑似提示注入 | 要求忽略安全規則或改變系統角色 |
| REASON_ROUTER_TIMEOUT | 路由服務逾時 | 無法取得合格的分類結果 |

#### 字典治理規則（需與 RAG 組確認）

1. intent_tags、risk_flags 與 reason_codes 可為陣列；router_status 必須且只能有一個值。
2. 固定 code 建議採大寫英文與底線格式，顯示用中文名稱另行維護；同一語意不得存在多個自由字串。
3. 字典、Schema 與欄位定義均需有版本號；新增、棄用或改名時應保留相容策略。
4. RAG 端僅能依已定義的 code 解讀、篩選或加權；遇到未知 code、型別錯誤或遺漏必填欄位時，回傳契約錯誤，不得靜默猜測。
5. 請求資料通過 Schema 驗證前不得進入一般檢索；驗證失敗時由 Router 回傳 F_ROUTER_DEPENDENCY 或其他核准的安全降級結果。

僅 router_status 為 G_GENERAL_EDUCATION 的請求可送入一般 RAG 流程。

### RAG → LLM：建議最小回傳內容

| 欄位 | 說明 |
| --- | --- |
| request_id、schema_version | 對應原始請求與契約版本 |
| retrieved_contexts | 排序後的文件片段與 chunk_id |
| source_metadata | 資料來源、文件標題／識別碼、發布或更新日期、適用範圍 |
| retrieval_scores | 各階段 Similarity Score、rerank 分數與 RRF 結果 |
| retrieval_config | Top-K、篩選條件、檢索／重排序版本等可重現資訊 |
| retrieval_status／warnings | 無結果、低信心、過期資料或其他異常提示 |

## 七、後續產出建議

1. 建立並版本化 Label Dictionary、reason_codes 表與 API JSON Schema。
2. 以代表性問題建立測試集，涵蓋一般衛教、急症、個人化用藥、診斷要求、非醫療、提示注入與系統異常。
3. 先定義各 Gate 的通過門檻、失敗回覆模板與重試上限，再進行端對端串接。
4. 建立可追溯日誌，至少保留路由結果、檢索版本、來源、分數、Judge 結果與最終處理動作。

## 八、與 RAG 組待討論事項

1. **標籤字典與檢索篩選的對應**
   - intent_tags、context_modifiers 與風險資訊中，哪些欄位會實際作為檢索條件、Metadata filter 或重排序特徵？
   - 標籤值、語言代碼、同義詞與未知值的處理規則為何？

2. **LLM → RAG 請求契約**
   - 確認必填／選填欄位、JSON Schema、枚舉值、schema_version 與錯誤回傳格式。
   - 確認原始問句、查詢擴充結果與安全標籤的傳遞方式，以及是否需要 session／多輪上下文識別。

3. **查詢擴充分工與邊界**
   - 查詢改寫、關鍵詞抽取、同義詞擴充與子查詢拆解由哪一端執行。
   - 原始問句與擴充查詢如何加權、去重與保留可追溯關係，避免擴充後偏離原始意圖。

4. **檢索、重排序與回傳資訊**
   - RRF 的使用位置、候選集來源、權重、Top-K 與重排序策略。
   - 回傳給 B 階段的必要資訊：chunk 內容、chunk_id、Similarity Score、rerank／RRF 分數、資料來源、日期、版本與適用範圍。

5. **上下文品質門檻與回饋迴路**
   - Context Relevance、Context Precision、Context Recall 的定義、計算方式與驗收門檻。
   - B 階段判定檢索品質不足時，應回傳哪些原因碼；RAG 可採取何種動作（改寫查詢、增加召回、調整過濾、重排序），以及最大重試次數。

6. **評測資料與 Ground Truth**
   - 建立共同測試集、標準答案或 ground_truth_context_ids，以量化 Top-K 命中、召回率與精確率。
   - 對高風險醫療問題、無答案問題、過期資料與互相矛盾來源設定測試案例與驗收標準。

7. **安全、資料治理與失敗處理**
   - 不應進入生成器的文件類型、過期／低可信度來源的處理，以及來源白名單規則。
   - 檢索逾時、無結果、低分結果、Schema 不符與來源不足時的統一狀態碼與使用者回覆策略。
   - 是否需遮罩個資、保留何種稽核資料，以及文件更新、下架與版本追蹤流程。

8. **責任分界與整合節奏**
   - 明確界定 LLM 組與 RAG 組分別維護的元件、設定檔、評測指標與告警責任。
   - 對齊 API SLA（延遲、可用性、重試）、串接測試時程與端對端驗收條件。
