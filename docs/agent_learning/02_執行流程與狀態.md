# 02｜執行流程與狀態

## 外層入口：run_workflow

入口在 `workflow/runner.py:105`。它負責：

1. 驗證 `RequestContext`。
2. 建立 `TraceRecorder`。
3. 補上未注入的預設元件。
4. 建立初始 `WorkflowState`。
5. 編譯並執行 LangGraph。
6. 將 graph state 收斂成 `WorkflowResult`。
7. 捕捉未處理 dependency error 並安全 fallback。

一個容易忽略的事實：預設值是離線 baseline。若沒有傳入 `agent_planner`，B insufficient 不會進 Agent。

## WorkflowState 的三類資料

`WorkflowState` 定義在 `workflow/graph.py:46`。

### 業務結果

- `a_result`
- `query_expansion`
- `rag_result`
- `b_result`
- `c_result`
- `d_result`

### Agent recovery state

- `original_query`：永遠保存原始使用者問題。
- `current_query`：可能被 Rewriter 更新。
- `agent_decision`：已通過 schema 驗證的 action。
- `previous_attempts`：已完成恢復動作及其 B 結果。
- `pending_agent_action`：rewrite 後等待下一次 B 記錄結果。
- `agent_steps`：Planner 已被計入的步數。
- `rewrite_count`、`clarification_count`：系統擁有的限制計數器。
- `retrieval_attempt`、`b_attempt`：trace 用的執行次數。
- `actions_taken`：已選 action 的簡表。

### 終止資料

- `status`
- `final_response`
- `fallback_reason`
- `termination_reason`
- `question`

## Graph 節點與轉移

| Node | 主要輸入 | 主要輸出 | 下一步 |
| --- | --- | --- | --- |
| A | request | `a_result` | Expansion 或 END |
| QUERY_EXPANSION | current query | retrieval queries | RAG |
| RAG | retrieval query | evidence | B |
| B | RAG result | canonical B result | C、Planner 或 END |
| AGENT_PLANNER | 縮減過的 context | validated decision | Ask、Rewrite 或 END |
| ASK_USER | missing fields | deterministic question | END |
| QUERY_REWRITER | original/current query | rewritten query | Expansion |
| C | B-approved evidence | candidate answer | D |
| D | A/B/C results | pass/fallback | END |

固定 edges 在 `workflow/graph.py:583–608`。

## 一次 rewrite 的狀態變化

假設初始 query 是 `吃 SGLT2 下體不舒服要注意什麼？`：

| 時點 | current_query | agent_steps | rewrite_count | previous_attempts |
| --- | --- | ---: | ---: | --- |
| 初始 | 原句 | 0 | 0 | `[]` |
| 第一次 B insufficient | 原句 | 0 | 0 | `[]` |
| Planner 選 rewrite | 原句 | 1 | 0 | `[]` |
| Rewriter 完成 | 改寫句 | 1 | 1 | `[]`，pending action 已設 |
| 第二次 B 完成 | 改寫句 | 1 | 1 | 加入 rewrite 與其 retrieval outcome |

`previous_attempts` 不是在 Planner 選 action 時立即加入；它要等 action 實際完成並再次取得 B 結果，才由 `b_node` 寫入。這讓歷史表示的是「已完成動作及結果」，而不是只有意圖。

## original_query 與 current_query

這兩個欄位刻意分離：

- Rewriter 只能更新 `current_query`。
- `original_query` 仍會留在後續 contract 與結果中。
- 每次改寫都能和原意比較。
- C 仍能知道真正的原始問題。

`_expand_current_query()` 在改寫後會以 current query 做檢索，但把 expansion result 的 `original_query` 維持為使用者原句。

## ASK_USER 的 re-entry

ASK_USER node 只建立問題並結束本次 workflow：

```text
status = NEEDS_CLARIFICATION
final_response = question
```

補充回答不是沿著原 graph 繼續，而是再次呼叫 `run_workflow()`。所以新輸入會重新經過 A。對應測試是 `test_clarification_reentry_goes_through_a_again`。

## WorkflowResult

外部得到的結果定義在 `workflow/schemas.py:16`。判讀 Agent 結果時優先看：

- `status`
- `agent_action`
- `agent_reason_code`
- `question`
- `current_query`
- `execution_history`
- `agent_steps`
- `rewrite_count`
- `termination_reason`
- `trace`

`reason_code` 主要用於 trace/evaluation；真正控制 graph 的是 `action`，而且仍須接受 graph 的上限檢查。
