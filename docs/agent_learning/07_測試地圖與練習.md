## 閱讀練習

### 練習 1：找出控制權

沿著 `planner_node()` 找出：

1. Planner 真正被呼叫的位置。
2. schema 驗證在哪裡完成。
3. rewrite limit 在哪裡覆蓋模型 action。
4. action 如何映射為 node。

答案位置：`planner.py:64–151`、`graph.py:329–470`。

### 練習 2：手動畫 state

用 AG-FALLBACK-001 畫出每一步的：

- `current_query`
- `agent_steps`
- `rewrite_count`
- `previous_attempts`
- `agent_decision`
- `termination_reason`

完成後再和 trace 比較。

### 練習 3：理解 requested vs executed

閱讀 `test_max_rewrite_enforcement_is_graph_owned`，先預測：

- Planner 回傳什麼？
- trace 的 `requested_action` 是什麼？
- 最後 `agent_action` 是什麼？
- Query Rewriter 是否被呼叫？

### 練習 4：檢查 ASK_USER 信號

把 `identified_missing_information=[]`，但讓 Scripted Planner 回傳 ASK_USER。思考目前是 schema、prompt 還是 graph 會拒絕它。

目前答案是：Pydantic schema 本身仍會接受有非空 `missing_information` 的 ASK_USER；真實 Planner 主要由 prompt 避免這種不一致。這是一個可新增 cross-field runtime validation 的改進點。

## 動手修改建議

依風險由低到高：

1. **新增測試，不改 production code**：增加「Planner 要求第二次 rewrite，被 graph 改為 fallback」案例。
2. **改善 trace**：額外記錄 decision 是否被 limit override。
3. **加強 ASK_USER runtime validation**：若 B 的 missing list 為空，graph 拒絕 ASK_USER。
4. **加強 rewrite validation**：將固定詞表擴充為可測試的 policy component。
5. **加入 durable clarification state**：設計跨 request 的 checkpoint，但仍要求重新經過 A。

## 修改時必守的不變條件

- Agent 不可繞過 A。
- Agent 不可批准 B evidence。
- Rewrite 後必須重跑 RAG/B。
- C 只能看到 B-approved evidence。
- D 仍是 mandatory final gate。
- limits 由系統而非模型擁有。
- 非法／失敗模型輸出必須安全終止。

## 建議的第一個實作任務

最適合用來驗證理解的是「ASK_USER action 與 B missing signal 的一致性檢查」：

```text
若 Planner 要求 ASK_USER
且 decision.missing_information 不屬於 B.identified_missing_information
→ 不執行詢問
→ 記錄 invalid planner decision
→ 安全 fallback
```

它會同時碰到 schema、planner context、graph enforcement、trace 與 tests，但改動範圍仍小，適合當作第一次深入實作。
