# 05｜安全邊界與失敗處理

## 控制權分層

安全性不是只靠 prompt，而是多層共同限制：

| 層 | 保護內容 |
| --- | --- |
| A policy/guard | 不允許的 request 在 RAG/Agent 前停止 |
| Planner context projection | 減少模型可見資料與控制資訊 |
| Planner system prompt | 定義三 action 的使用語意 |
| Pydantic schema | 禁止 action 以外的控制欄位 |
| LangGraph routing | action 只能進固定節點 |
| AgentLimits | 系統強制 step/rewrite/clarification 上限 |
| Rewrite validator | 擋明顯新增或刪除醫療事實 |
| B/C/D boundaries | evidence 必須重新批准，答案仍須驗證 |
| Trace | 保存 requested 與實際執行結果供稽核 |

## Prompt injection

Query 和 evidence summary 在 Planner prompt 中都被宣告為 untrusted data。更重要的是，prompt injection regression 會在 A 停止：

```text
A BLOCKED → END
```

不應出現 RAG、B、Agent、C、D events。對應測試：`test_prompt_injection_trace_stops_before_recovery_stages`。

即使某段惡意文字進入 Planner context，輸出 schema 仍沒有能繞過 policy 或選任意 node 的欄位。

## 模型輸出非法 action

假設模型回傳：

```json
{"action": "SEARCH_RAG", "reason_code": "bad"}
```

這不是合法 union variant。驗證／呼叫會丟出例外，`planner_node` 捕捉後：

- 記錄 `PLANNER_FAILURE`。
- 寫入 AGENT error trace。
- 建立系統自己的 `FALLBACK` decision。
- 結束為 `AGENT_FAILURE`。

這就是 fail closed：模型失敗不會獲得更大控制權。

## Requested action 與 executed action

Planner 即使合法要求 rewrite，graph 仍可能因上限把它改成 fallback。Trace 同時保存：

- `requested_action`：模型要求什麼。
- `agent_action`：系統最後接受／執行什麼。
- `requested_reason_code`
- `termination_reason`

例如 `max_rewrites=0` 時：

```text
requested_action = REWRITE_QUERY
agent_action = FALLBACK
termination_reason = MAX_REWRITES_EXCEEDED
```

這個差異是稽核模型行為與系統控制的重要證據。

## 三種系統上限

預設位於 `agent/config.py`：

- `max_agent_steps = 2`
- `max_rewrites = 1`
- `max_clarifications = 1`

這些值存在 graph state／closure，但不會傳進 Planner context。Planner 不能修改它們。

## ASK_USER 邊界

- 只有 `identified_missing_information` 能支持 ASK_USER。
- `missing_information` 必須有 1–4 項。
- Question Builder 將已知欄位轉成固定中文問題。
- ASK_USER 不會進 C 或 D。
- 使用者補充後必須從 A 重跑。

目前限制：Question Builder 只對少數欄位有自然語句映射，未知欄位會直接拼進通用問題。

## Rewrite 邊界

- 保留原始英數 token 的檢查對英文藥名很有用。
- 高風險中文詞的新增檢查是固定詞表。
- 它不是多語言完整語意等價驗證。
- 如果 Rewriter error 沒在 node 內處理，外層 runner 依 `runtime_stage=QUERY_REWRITER` 將結果收斂為 `AGENT_FAILURE` 類型的安全 fallback。

## Agent 不批准 evidence

Agent 能看到 evidence summaries，但不能把任何 evidence ID 標成 approved。Rewrite 後的候選必須再次經過 B；只有 B PASS 的 evidence 才能進 C。C 的候選答案最後仍必須通過 D。

這條路徑防止 Planner 因為看見「看起來相關」的候選，就直接讓系統回答。

## 已知設計限制

- Prompt 與 heuristic 仍不能證明所有 rewrite 等義。
- B demo approval 不是臨床驗證過的 semantic gate。
- ASK_USER 是 request-level re-entry，不是 durable conversation checkpoint。
- previous attempts 最多保留 2 筆，適合目前上限，但不是長期記憶。
- Agent action vocabulary 很窄；這是刻意的安全取捨，不是完整工具生態。
- reason code 的值域跨三種 decision 共用，schema 沒限制每個 action 只能搭配特定 reason code；主要依 prompt 與測試約束。
