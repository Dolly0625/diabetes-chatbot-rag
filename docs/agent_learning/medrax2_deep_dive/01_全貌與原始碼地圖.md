# 01｜全貌與原始碼地圖

## 先建立正確心智模型

MedRAX2 不是一張很複雜的 LangGraph。它是一個很小的通用 ReAct loop，外接大量異質醫療工具、模型資源、RAG、API、UI 與 benchmark。

```text
複雜度較低                         複雜度較高

Agent graph ───→ tool wrappers ───→ model loading / GPU / data / UI / deployment
  2 nodes          統一介面             異質依賴與生命週期
```

因此不能用 graph node 數量判斷專案成熟度，也不能把「有很多模型」誤認為「Agent orchestration 很複雜」。

## 五層架構

| 層 | 主要檔案 | 責任 |
| --- | --- | --- |
| Entry/configuration | `main.py` | 解析設定、建立 model、選擇性載入 tools、建立 Agent |
| Orchestration | `medrax/agent/agent.py` | message state、LLM/tool loop、終止判斷 |
| Capability adapters | `medrax/tools/**` | 將影像模型、RAG、搜尋、DICOM、sandbox 包成 LangChain tool |
| Model/data services | `medrax/models/**`、`medrax/rag/**` | 模型供應商、embedding、Pinecone、reranking、RetrievalQA |
| Product/evaluation | `interface.py`、`api.py`、`web_platform/**`、`benchmarking/**` | UI/API、檔案處理、thread、tool lifecycle、benchmark |

### Layer 1：入口與組裝

[`main.py`](https://github.com/bowang-lab/MedRAX2/blob/dcd6b852f3f9557640159e200fab5f0acdea39ff/main.py#L112-L215) 做的不是醫療推理，而是 dependency assembly：

```python
def initialize_agent(..., tools_to_use=None, model="gpt-4.1", ...):
    prompts = load_prompts_from_file(prompt_file)
    prompt = prompts[system_prompt]

    all_tools = {
        "TorchXRayVisionClassifierTool": lambda: ...,
        "MedicalRAGTool": lambda: RAGTool(config=rag_config),
        "DuckDuckGoSearchTool": lambda: DuckDuckGoSearchTool(),
        # ...
    }

    tools_dict = {}
    for tool_name in tools_to_use or []:
        if tool_name in all_tools:
            tools_dict[tool_name] = all_tools[tool_name]()

    checkpointer = MemorySaver()
    llm = ModelFactory.create_model(model_name=model, ...)
    agent = Agent(llm, tools=list(tools_dict.values()),
                  system_prompt=prompt, checkpointer=checkpointer)
    return agent, tools_dict
```

這裡同時完成四種 binding：

1. prompt 綁定到 Agent。
2. model provider 綁定到 LangChain LLM。
3. selected tool instances 綁定到 model。
4. checkpointer 綁定到 compiled graph。

### Layer 2：Agent loop

[`medrax/agent/agent.py`](https://github.com/bowang-lab/MedRAX2/blob/dcd6b852f3f9557640159e200fab5f0acdea39ff/medrax/agent/agent.py) 只有 121 行。它不認識 X 光分類、RAG 或 DICOM；它只認識：

- messages；
- 一個可 `invoke()` 的 model；
- 一組 `BaseTool`；
- AI response 有沒有 `tool_calls`。

這是良好的 capability inversion：Agent loop 不依賴特定醫療模型，醫療能力透過 tool interface 注入。

### Layer 3：工具 adapter

一個典型工具包含：

```text
Pydantic input schema
name
description
_run() / _arun()
model/resource state
output + metadata
```

例如分類器、VQA、DICOM 內部技術完全不同，但對 Agent 都呈現 `BaseTool`。這是 MedRAX2 最值得借鏡的部分之一。

### Layer 4：服務實作

`RAGTool` 並不自己完成所有 RAG 工作。它把工作轉交給 `CohereRAG`：

```text
RAGTool._run(query)
→ RetrievalQA.invoke({"query": query})
→ Pinecone similarity search
→ Cohere rerank
→ Cohere LLM generation
→ answer + source_documents
```

同理，影像 tool wrapper 只是負責 schema、前後處理和錯誤 envelope，真正模型推論在 tool instance 內部。

### Layer 5：產品層

MedRAX2 至少存在三種使用面：

- 舊版 Gradio `interface.py`；
- FastAPI `api.py`；
- 較完整的 `web_platform/` 前後端。

這些層負責 graph 本身不負責的事情，例如：

- 上傳檔案；
- 產生或沿用 `thread_id`；
- 將影像同時轉成路徑與 base64；
- 顯示 tool call 與 tool result；
- 管理大型工具載入、卸載與 GPU placement；
- 保存 chat、patient、scan、tool execution 等產品資料。

## Request 從哪裡進、從哪裡出

以 FastAPI 為例：

```text
POST /query-with-images
→ 驗證 MIME type
→ 暫存上傳檔案
→ 建立 image_path message
→ 建立 base64 image_url message
→ 建立 text message
→ workflow.stream(..., thread_id)
→ 收集 AIMessage / ToolMessage updates
→ 清理暫存檔
→ QueryResponse
```

注意：API response 的 `tools_used` 在該快照中只記成通用字串 `tool_executed`，不是實際 tool name。這表示「UI 可看到 pending tool call name」和「API 回傳準確工具清單」是兩個不同的實作品質。
