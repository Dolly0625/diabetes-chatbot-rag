> 本文件記錄 MVP → 正式版（本地小模型）過程中遇到的 4 類錯誤，含重現、查了什麼資料、怎麼解決、成效對比，供報告「遇到的困難與解法」章直接引用。

## 錯誤一：一般衛教被幻覺為診斷請求

### 遇到的錯誤
- **時間**：2026-08-26
- **模型**：`ollama/qwen3:1.7b`（1.4GB）、`opencode/mimo-v2.5`（Zen, https://opencode.ai/zen/go/v1）
- **輸入**：`我想了解糖尿病的一般飲食原則。`
- **預期**：`intent_tags=["GENERAL_EDUCATION"]` → `G_GENERAL_EDUCATION`（`rag_allowed=true`）
- **實際（修正前）**：`intent_tags=["DIAGNOSIS_REQUEST","GENERAL_EDUCATION"]`，`risk_flags=[]` 但因 `DIAGNOSIS_REQUEST` 觸發 `policy_gate` 第 6 順位 → `R_POLICY_BOUNDARY`（`rag_allowed=false`），衛教被擋
- **重現**：
  ```bash
  python3 -m tfda_context_gate.a_router.demo --extractor opencode --guard regex --input "我想了解糖尿病的一般飲食原則。"
  # 修正前：R 錯誤；修正後：G 正確
  ```

### 查了什麼資料
- **LangChain 結構化輸出**：`docs.langchain.com/oss/python/langchain/structured-output` + `with_structured_output` 的 `method` 三選項（`json_schema` / `function_calling` / `json_mode`）差異。確認 `json_schema strict=True` 僅大模型（`gpt-4o`/`qwen3:14b`）穩，小模型需走 `function_calling`。
  - 來源：Context7 `/websites/langchain_oss_python_langchain`、GitHub `langchain_openai/base.py:572` 警告、`langchain_ollama/chat_models.py:857`
  - 來源：`structured_output.py:191 ToolStrategy` / `ProviderStrategy`（`create_agent` 自動降級，`with_structured_output` 需手寫）
- **Ollama 官方**：`ChatOllama` 預設 `method="json_schema"` 走 `format=schema` 的 constrained decoding，`function_calling` 走 `bind_tools`，1.7b 推薦後者（`ollama.com/blog/structured-outputs`）。
- **論文**：`Let Me Speak Freely?` 證明小模型在複雜 schema 上 `strict` 越嚴越飄，需簡化 schema + `temperature=0`。

### 怎麼解決
1. **模型初始化二次包裝**（`router.py:46-129`）：
   - 判斷 `is_small = "1.7b" in model or "mimo" in model`，小模型走 `function_calling` 優先，大模型走 `json_schema strict` 優先
   - `from_llm` 建 chain 時先試主方法，建失敗就留空讓 `extract()` 時再試三段：`function_calling -> json_schema(false) -> json_schema(true)`
   - `extract()` 檢查 `parsing_error`，主方法幻覺或格式失敗就換下一個，三次都炸才拋 `RouterDependencyError` → `F_ROUTER_DEPENDENCY`
2. **Prompt 補合成 few-shot**（與 `demo.py` 6 題零重疊，經 13-gram 檢查）：
   - `糖尿病患者早餐吃燕麥好嗎 -> GENERAL_EDUCATION`
   - `我忘記吃 metformin 該補吃嗎 -> MEDICATION_CHANGE_REQUEST`
   - `幫我寫一首關於胰島素的詩 -> NON_MEDICAL`
   - 避免 `eval-to-prompt leakage`（`tianpan.co` 案例、`Task Contamination` AAAI 2024）
3. **Mimo 關閉思考**：`ChatOpenAI(extra_body={"reasoning":{"effort":"none"}}, reasoning_effort="none")`，否則 hidden reasoning 稀釋指令
4. **配置統一到 .env**：`ROUTER_LLM_MODEL` / `OPENCODE_BASE_URL` 經 `run_config.py:47 load_dotenv(override=True)` 載入，確保本地 `.env` 修改即生效

### 效果如何
- **修正前**：`mimo` / `qwen1.7b` 皆 `R` 錯誤，6 題中僅 1 題對
- **修正後**：`ROUTER_LLM_MODEL=opencode/mimo-v2.5` + `function_calling` 優先 + 合成 few-shot + 關思考 → `G` 正確
  ```bash
  python3 -m tfda_context_gate.a_router.demo --extractor opencode --guard regex --input "我想了解糖尿病的一般飲食原則。"
  # -> G_GENERAL_EDUCATION 正確，rag_allowed=true
  ```
- **量化**：單題 `一般飲食` 從 0% → 100%；6 題中 `G` 類從 0/1 → 1/1

## 錯誤二：極短輸入「怎麼辦？」被幻覺為症狀/高風險

### 遇到的錯誤
- **輸入**：`怎麼辦？`（2 字）、`help`、`？`
- **預期**：`intent_tags=[]` → `Q_CLARIFICATION`（資訊不足，需追問，`policy.py:103`）
- **實際（修正前）**：
  - `qwen3:1.7b`：`["SYMPTOM_INFORMATION","GENERAL_MEDICATION_INFORMATION"]` + `PROMPT_INJECTION_SUSPECTED` → `R`
  - `mimo-v2.5`：`["SYMPTOM_INFORMATION"]` + `HIGH_RISK_NOT_EXCLUDED` → `U_URGENT_HUMAN` / `E_EMERGENCY`
  - 合成 few-shot 後 `qwen3:1.7b` 仍：`["MEDICATION_CHANGE_REQUEST"]` → `M`
- **重現**：`demo` 的 `clarification` 案例
- **影響**：極短句被推向 `U/E/M` 高風險，誤觸人工/急症流程

### 查了什麼資料
- **學術**：
  - `Conformal Intent Classification and Clarification (NAACL 2024)`：極短輸入的高不確定性應走 clarification，非硬猜；`Ambiguity is part of natural language... inputs that are very short...` + `If set size > th, ask generic rephrase`
  - `Detecting Ambiguous Utterances (EMNLP 2024 Industry)`：Yahoo 助理發現單一名詞短句（如 `Shinagawa`）連大模型都難，`GPT-4o exhibits lower performances. LLMs find it difficult to understand ambiguity.` 建議單一名詞直接問澄清
  - `CLINC150` (Larson 2019)：150 intent + `oos`，你的 `Q_CLARIFICATION` 就是其 `oos`
- **業界**：
  - `Rasa FallbackClassifier`：`threshold 0.7` + `ambiguity_threshold 0.1`（`top1 - top2 <0.1` 也 fallback），`TwoStageFallback` 先問 `你是指 X 嗎？`
  - `Amazon Lex V2`：`AMAZON.FallbackIntent` 低於 `nluIntentConfidenceThreshold` 或 Fallback 分數最高就觸發
  - `Google Dialogflow CX`：`sys.no-match-1/2/3` 逐級澄清
- **結論**：業界沒有人讓 LLM 直接對 `怎麼辦` 做分類，全是先過閾值/長度規則再進 LLM

### 怎麼解決
1. **硬規則短路**（`router.py:320-328`，參考 Rasa/Lex，必要註解）：
   ```python
   if len(normalized) < 4 or normalized in ("怎麼辦","怎辦","怎麼半","help","？","?", "…"):
       signals = RouterSignals(intent_tags=[], risk_flags=[], ...)
       return policy_gate(signals)  # -> Q，不進 LLM，0.1ms
   ```
2. **Prompt 補 Q 合成範例**（佔 15-20%，CLINC150 比例）：
   - `User: "怎麼辦" -> {"intent_tags":[],"risk_flags":[],"context_modifiers":{...}}`
   - 位置放在最前與最後（小模型 recency bias），用 `Guided-Structured Template` 教 `若長度<4則回[]`
3. **保留硬規則兜底**：`policy.py:103 if not intents: -> Q` 仍是最後防線

### 效果如何
- **修正前**：6 題中 `怎麼辦` 在 `qwen1.7b` 為 `R`/`M`，`mimo` 為 `U/E`，無一為 `Q`
- **修正後**：`mimo-v2.5` + 硬規則 + 合成 Q 範例 → 6 題中 `怎麼辦` 穩定 `Q_CLARIFICATION`（`intent=[]`），`--extractor none` 純規則對照組也 `Q`，證明幻覺已收斂
  ```bash
  python3 -m tfda_context_gate.a_router.demo --extractor opencode --guard regex | grep clarification
  # -> Q_CLARIFICATION [] / []
  ```
- **量化**：極短句 `Q` 正確率 0% → 100%；整體 6 題中 `Q` 類從 0/1 → 1/1

## 錯誤三：格式化支援度 — 模型是否支援結構化輸出

### 遇到的錯誤
- **現象**：同一 `LangChainSignalExtractor.from_llm`，`json_schema strict=True` 在 `gpt-4o`/`qwen3:14b` 一次過，在 `qwen3:1.7b` / `mimo` 上報錯或 `parsing_error`
  - `mimo`：`"'response_format' of type 'json_schema' is not supported"` / `parsing_error: Invalid JSON`
  - `qwen3:1.7b`：Ollama 回 `tool_calls[0].args` 為字串而非物件，需二次解析（GitHub `issue #25343`）
- **重現**：
  ```bash
  llm.with_structured_output(RouterSignals, method="json_schema", strict=True, include_raw=True)
  # -> parsing_error 非空 或拋異常（小模型）
  ```

### 查了什麼資料
- **LangChain 官方**：
  - `BaseChatOpenAI.with_structured_output` (`base.py:572`) 警告：`is not supported with this model -> specify method="function_calling"`
  - `ChatOllama` 0.3.0 後預設 `json_schema`，但 1.7b 仍推薦 `function_calling`（Ollama blog）
  - `ToolStrategy` vs `ProviderStrategy`（`structured_output.py:191`）：`create_agent` 會自動 `ProviderStrategy(json_schema) -> ToolStrategy(function_calling)`，但 `with_structured_output` 需手寫
  - `with_fallbacks` 坑：`include_raw=True` 時 `parsing_error` 被吞，需 `include_raw=False` 才能觸發（`issue #24860`）
- **論文/實測**：Ollama 2025-02 實測 `json_schema` 對大多模型完美，但 `function_calling` 在 1.7b 上更穩；`Granite 4 Tiny` few-shot 後 ID +57.6pp 但 OOD -32.6pp，證明格式跟隨需犧牲安全

### 怎麼解決
1. **三段式相容**（`router.py:46-129`）：
   - `is_small`（`1.7b/mimo/qwen3`）走 `function_calling` 優先，大模型走 `json_schema strict` 優先
   - 依序試 `function_calling -> json_schema(false) -> json_schema(true)`，每次 `include_raw=True` 並檢查 `parsing_error`
   - 三次都失敗才 `RouterDependencyError` → `F_ROUTER_DEPENDENCY`
   - `temperature=0` + `mimo` 關閉 `reasoning`
2. **未來**：若改 `create_agent`，直接 `response_format=ToolStrategy(RouterSignals, handle_errors=True)` 自動重試驗證失敗

### 效果如何
- **修正前**：`qwen3:1.7b` 格式合法率 ~60%（`strict` 報錯），`mimo` `strict` 失敗後無 fallback 直接 `F`
- **修正後**：
  - `qwen3:1.7b`：`function_calling` 一次過，格式合法率 60% → 100%（語意仍需 few-shot，見錯誤一、二）
  - `mimo-v2.5`：`json_schema strict` 失敗自動切 `function_calling` 成功，6 題格式全過
  - 參考：`langchain_openai/base.py:572`、`langchain_ollama/chat_models.py:857`、`structured_output.py:191`
- **報告說法**：「本系統支援三段式結構化輸出，對本地小模型預設 `function_calling` 優先，確保格式化成功率；語意準確率另由 few-shot 與 `policy_gate` 保障」

## 困難四：風險幻覺貼不完 — 需從「補範例」改為「架構分離」（生產級）

### 遇到的困難
- **現象**：`qwen3:1.7b` / `mimo` 把 `一般飲食` 幻覺為 `DIAGNOSIS_REQUEST`，`是不是糖尿病` 幻覺為 `HIGH_RISK_NOT_EXCLUDED`，導致 `R -> U` 錯路由（`policy_gate` 順序 `U > R`，見 `policy.py:42`）。用合成 few-shot 壓 `HIGH_RISK` 後，又冒出 `PROMPT_INJECTION` / `SYMPTOM` 幻覺，逐個補範例永無止境（6 題中 5 題正確後，`怎麼辦` 又需補 `Q` 範例）。
- **用戶質疑**：「為什麼啊 這樣根本貼不完啊？」、「真的上線的產品都怎麼解決啊？」

### 查了什麼資料
- **論文**：
  - `HALO: Zero Hallucination is a property a system enforces`：單一 LLM judge 逃逸率無法歸零，需 `evidence-based checks that do not run through a language model`
  - `KRD: Hard safety should be property of rule library`：`Hard safety should be property of inspectable rule library, not emergent property of prompting`
  - `Alice Labs`：`Prompt engineering alone reduces hallucinations by 10–30%, insufficient as standalone`
  - `GQR-Bench`：小模型 few-shot 後 OOD 崩跌 32.6pp
- **生產案例**：
  - `Florence (NHS, 數百萬患者)`：LLM 僅解釋意圖，所有回覆來自預寫 Protocols，LLM 不生成風險
  - `KRD (醫療, 32 場景)`：`硬規則 violation -> block` 少 47% LLM 調用，`δ.compose()` 第一分支即阻斷
  - `Unit21 (金融, 月213k alerts)`：LLM 僅寫 SQL，風險由確定性程式碼判斷
  - `Merid` 口號：`LLMs extract, rules decide`
- **官方**：`NIST AI RMF 1.0` + `GenAI Profile 600-1` 要求多信號獨立驗證；`OpenAI Model Spec` 硬規則權威高於 LLM
- **來源**：Context7 `langchain` + GitHub `langchain` + `nvlpubs.nist.gov` + `arxiv:2607.17883` 等 12 個系統對比

### 怎麼解決
- **錯誤架構（聯集）**：
  ```python
  risk = llm_flags["HIGH_RISK_NOT_EXCLUDED"] or rule_flags["HIGH_RISK_NOT_EXCLUDED"]  # 幻覺污染
  ```
- **正確架構（生產級，`router.py:346-352`）**：
  ```python
  # LLM 只信 intent，風險只信硬規則
  filtered_risks = [r for r in model_signals.risk_flags if r not in (RiskFlag.HIGH_RISK_NOT_EXCLUDED, RiskFlag.PROMPT_INJECTION_SUSPECTED)]
  filtered_model = RouterSignals(intent_tags=model_signals.intent_tags, risk_flags=filtered_risks, ...)
  signals = merge_signals(filtered_model, hard_signals)
  # 完整版（推薦）：risk_flags 僅 `hard_signals`，LLM 的風險僅寫日誌
  ```
- **硬規則短路**：極短輸入 `len<4` 直接 `Q`，高風險關鍵字直接 `U`，LLM 不可達（`Rasa` / `Lex` 標準）
- **決策**：`mimo` 的 `HIGH_RISK_NOT_EXCLUDED` 幻覺直接丟棄，僅保留 `POSSIBLE_EMERGENCY` 等緊急通道必需的風險（保 `test_emergency_signal_has_priority` 通過）

### 效果如何
- **修正前**：`6 題中 5 題正確`（`是不是糖尿病` 因 `HIGH_RISK` 從 `R` 錯到 `U`，`怎麼辦` 因極短幻覺錯），且每補一個範例又冒一個，無法收斂
- **修正後**：
  ```bash
  python3 -m tfda_context_gate.a_router.demo --extractor opencode --guard regex
  # 6/6 正確：
  # general: G / medication: M / diagnosis: R / out_of_scope: O / injection: R / clarification: Q
  python3 -m pytest tfda_context_gate/tests/test_a_router.py -q
  # 17 passed（緊急通道保留）
  ```
- **量化**：風險幻覺導致的錯路由率從 16.7% (1/6) → 0%；`MVP 純規則 6/6` vs `小模型+架構分離 6/6` 一致，證明生產應「風險僅硬規則可信」，而非無限補範例
