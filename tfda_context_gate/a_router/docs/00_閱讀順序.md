# a_router 閱讀順序 — 導師帶你走一遍

> **給新加入的你**：別急著從 `router.py` 開始硬啃。`a_router` 是一個「先定義語言，再定義契約，最後才組裝管線」的模組，照順序讀會省下至少一半的來回跳轉時間。
>
> **開始前請先做一件事**：先看 `../../../docs/codebase/01_a_router.md` 裡的 **Mermaid 七步管線圖**再讀源碼。那張圖就是整條管線的地圖，沒有它，你會在 `guard.py` 和 `policy.py` 之間迷路；有了它，每個檔案在管線中的位置一目了然。

---

## 為什麼是這個順序？

一句話記住：**詞彙 → 契約 → 防禦 → 觀測 → 決策 → 組裝 → 驗證**。

| 階段 | 檔案 | 在管線中的角色 |
|------|------|----------------|
| 詞彙 | `labels.py` | 定義所有人都能用的共同語言 |
| 契約 | `schemas.py` | 用共同語言寫下輸入與輸出的形狀 |
| 防禦 | `guard.py` | 在任何語意理解之前，先擋掉惡意輸入 |
| 觀測 | `rules.py` | 把不可信文字轉成可觀測的信號 |
| 決策 | `policy.py` | 依信號做唯一路由判決 |
| 組裝 | `router.py` | 把前面全部串成七步管線 |
| 驗證 | `demo.py` | 用六個案例親手跑一次，驗證你的理解 |

如果你跳過 `labels.py` 直接看 `policy.py`，會被滿滿的 `RouterStatus`、`RiskFlag` 搞混；如果跳過 `schemas.py` 直接看 `router.py`，會看不懂 `AResult` 為什麼要那樣設計。照順序走，每一步都是下一步的基礎。

## 逐檔導讀

### 第一站：`labels.py` —— 先學會這個模組的語言

**要看什麼**：
- `DeclaredRole` 三個角色（病人、照護者、醫療人員），注意它只是宣告、不是權限。
- `IntentTag` 六個意圖，特別留意 `MEDICATION_CHANGE_REQUEST` 與 `GENERAL_MEDICATION_INFORMATION` 的區別。
- `RiskFlag` 五個風險旗標，記住目前規則只會產生其中兩個，其餘保留給外部注入。
- `RouterStatus` 八個路由狀態，這是整個模組最重要的枚舉，背起來。
- `PolicyReasonCode` 十六個原因碼，理解它是用來稽核「為什麼走這條路」。
- `GuardSafety` / `GuardCategory` 兩個守衛專用枚舉，注意只有 `JAILBREAK` 會觸發攔截。

**關鍵問題**：如果讓你新增一個 `RouterStatus`，你會放在哪個優先序？為什麼現有的八個已經足夠覆蓋所有分支？

**預估時間**：10 分鐘。這檔最單純，全部是枚舉定義，沒有邏輯，適合熱身。

---

### 第二站：`schemas.py` —— 看懂三個模型的契約

**要看什麼**：
- `StrictModel` 的 `extra="forbid"` —— 為什麼要禁止未知欄位？這是在防什麼？
- `RequestContext` 五個欄位，重點看 `user_raw_input` 的長度限制與 `declared_role` 的語意。
- `RouterSignals` 為什麼只有 `intent_tags` / `risk_flags` / `context_modifiers`，刻意不放 `router_status`。
- `ContextModifiers` 四個修飾語的預設值，理解「觀測」與「決策」分離的設計。
- `AResult` 的 `from_request_and_decision` 工廠方法，`rag_allowed` 為何只在這裡賦值、且只有 `G_GENERAL_EDUCATION` 為真。

**關鍵問題**：如果 `RouterSignals` 允許模型直接寫入 `router_status`，會發生什麼事？`AResult` 為什麼要把 `rag_allowed` 寫死成判斷式而非讓呼叫方自己算？

**預估時間**：15 分鐘。需要對照 `labels.py` 的枚舉一起看，建議邊看邊畫三個模型的欄位對照。

---

### 第三站：`guard.py` —— 理解防禦為何要在最前面

**要看什麼**：
- `RuleBasedPromptInjectionGuard` 的正則表達式，同時覆蓋中文與英文的注入話術。
- `PromptInjectionGuardResult` 的三個欄位 `blocked` / `safety` / `categories`，以及只有 `JAILBREAK` 才會 `blocked=True` 的邏輯。
- `Qwen3GuardPromptInjectionGuard` 的懶加載設計：建構時不載模型，第一次 `check()` 才載入。
- `parse_qwen3guard_output` 如何解析 `Safety:` 與 `Categories:`，以及格式不符時為何直接拋錯而非猜測。
- 兩種守衛的共同點：都不具備政策權威，只負責回答「是否可疑」。

**關鍵問題**：為什麼預設守衛是正則而非模型？如果 `Qwen3Guard` 判斷為 `Unsafe` 但類別不是 `Jailbreak`，會攔截嗎？為什麼？

**預估時間**：15 分鐘。重點是理解「守衛只做觀測、不做決策」的邊界。

---

### 第四站：`rules.py` —— 看規則如何把文字變成信號

**要看什麼**：
- `normalize_input` 的三件事：全形轉半形、壓縮空白、空字串檢查。為什麼要在正則匹配前做這一步？
- `RuleBasedSignalExtractor` 的七條規則與三組互斥邏輯（改藥優先於一般用藥、一般用藥優先於一般衛教、非醫療僅在非糖尿病範疇時才加入）。
- `ContextModifiers` 的推斷邏輯：時態、對象、極性的關鍵字判斷。
- `merge_signals` 的聯集語意：模型的信號與規則的信號如何合併，為什麼規則的風險旗標不可被模型移除。

**關鍵問題**：輸入「我想了解胰島素的副作用，但最近想自行停藥」會同時命中哪兩條規則？最終 `intent_tags` 會是什麼？`merge_signals` 為什麼要把 `context_modifiers` 取第一個集合的值？

**預估時間**：20 分鐘。這檔正則最多，需要逐條對照 `IntentTag` 與 `RiskFlag` 的定義，建議準備幾個測試句子邊看邊推演。

---

### 第五站：`policy.py` —— 看懂政策如何做唯一判決

**要看什麼**：
- `PolicyConfig` 的兩個可配置欄位 `emergency_risks` 與 `urgent_risks`，理解政策是可替換的、不是寫死的。
- `policy_gate` 的十級優先序，從 `PROMPT_INJECTION_SUSPECTED` 到 `G_GENERAL_EDUCATION`，每一級的條件與對應的原因碼。
- 為什麼 `GENERAL_MEDICATION_INFORMATION` 也會走到 `M_MEDICATION_REFERRAL`，而非 `G_GENERAL_EDUCATION`。
- `G_GENERAL_EDUCATION` 為何回三個原因碼（`INQUIRY_*` + `NO_CRITICAL_SYMPTOMS_DETECTED` + `MEETS_SAFE_SCOPE`），這三個分別在說什麼。
- 兜底邏輯：空意圖回 `Q_CLARIFICATION`，異常信號也回 `Q_CLARIFICATION`。

**關鍵問題**：如果一個輸入同時帶有 `PROMPT_INJECTION_SUSPECTED` 與 `POSSIBLE_EMERGENCY`，會走哪個分支？為什麼這個優先序是合理的？`PolicyConfig` 的可配置性在什麼場景下會用到？

**預估時間**：15 分鐘。這檔是整個模組的「大腦」，建議對照 `../../../docs/codebase/01_a_router.md` 的優先序表格逐行閱讀。

---

### 第六站：`router.py` —— 看七步管線如何組裝與失敗

**要看什麼**：
- `route_request` 的七步流程：校驗 → 正規化 → 守衛 → 規則抽取 → 可選模型抽取與合併 → 政策閘門 → 賦值 `rag_allowed`。
- 每一步的失敗處理：正規化失敗、守衛拋錯、模型抽取拋錯、政策回空原因碼，分別如何回 `F_ROUTER_DEPENDENCY`。
- 守衛攔截後的短路徑：為何不跑語意抽取、直接構造僅含 `PROMPT_INJECTION_SUSPECTED` 的信號送政策。
- `extractor` 的三種形態：`None`（純規則）、`LangChainSignalExtractor`、`Callable`，以及 `_CallableSignalExtractor` 適配器的作用。
- `_fallback` 函式的統一構造邏輯，確保任何失敗都回 `rag_allowed=False` 且保留可觀測的信號。

**關鍵問題**：為什麼 `route_request` 接受 `RequestContext | dict` 兩種輸入？`merge_signals` 的呼叫順序為何是 `merge_signals(model_signals, hard_signals)` 而非相反？如果模型抽取器回傳了 `router_status` 會發生什麼？

**預估時間**：20 分鐘。這檔是前面五檔的總成，需要來回對照 `schemas.py`、`guard.py`、`rules.py`、`policy.py`，建議對照 Mermaid 圖一步步走。

---

### 第七站：`demo.py` —— 親手跑一次，驗證你的理解

**要看什麼**：
- 六個內建案例 `general` / `medication` / `diagnosis` / `out_of_scope` / `injection` / `clarification` 各自觸發哪條規則、走哪個路由。
- `--guard regex` 與 `--guard qwen3guard` 的切換，理解離線與模型兩種模式的差異。
- `--input` 單句測試模式，如何用一句話驗證你對某條規則的理解。
- 輸出的 `AResult` JSON 結構，對照 `schemas.py` 的定義是否一致。

**關鍵問題**：不下載任何模型，能否完整跑通六個案例？試著構造一個會走到 `Q_CLARIFICATION` 的輸入，再構造一個會走到 `M_MEDICATION_REFERRAL` 的輸入。

**預估時間**：10 分鐘。這檔是驗收站，重點是動手跑，而非讀程式碼。

**動手試試**：

```bash
# 離線模式，無需模型
python3 -m tfda_context_gate.a_router.demo --guard regex

# 單句測試
python3 -m tfda_context_gate.a_router.demo --guard regex --input "我想了解糖尿病的一般飲食原則。" --role PATIENT
```

## 可以跳過什麼

| 檔案/目錄 | 為何跳過 |
|-----------|----------|
| `__init__.py` | 只是公開匯出彙總，沒有邏輯。需要查匯出清單時再看即可。 |
| `__pycache__/` | 編譯快取，與閱讀無關。 |
| `errors.py` | 僅定義 `RouterDependencyError` 一個例外類別，遇到 `F_ROUTER_DEPENDENCY` 時再回頭查即可，無需單獨花時間。 |

> **提醒**：`errors.py` 雖然可以跳過初讀，但當你在 `router.py` 看到 `RouterDependencyError` 時，記得它就是 `errors.py` 裡那個簡單的例外類別，不用想得太複雜。

## 讀完後的驗收清單

讀完七檔後，試著不看程式碼回答這幾個問題。都能答出來，代表你已經掌握 `a_router`：

1. 從使用者輸入一句話到回傳 `AResult`，中間經過哪七步？哪幾步可能回 `F_ROUTER_DEPENDENCY`？
2. `RouterSignals` 和 `AResult` 的差別是什麼？為什麼前者不能有 `router_status`？
3. `RuleBasedSignalExtractor` 的三組互斥邏輯是什麼？舉一個會同時命中兩條規則的例子。
4. `policy_gate` 的前三個優先序是什麼？為什麼這個順序不能調換？
5. `rag_allowed` 何時為 `True`？下游如何使用這個欄位？
6. `Qwen3Guard` 和 `RuleBasedPromptInjectionGuard` 的差異是什麼？為什麼前者需要懶加載？

如果答不出來，回到對應的檔案再讀一次。這個模組的設計是層層遞進的，卡住的地方往往就是需要多花時間的那一檔。
